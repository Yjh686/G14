## 1. 总体设计

### 1.1 认证流程

```
① 用户输入 账号 + 密码            →  POST /api/auth/login
② 后端按账号查库自动识别角色       →  学号→STUDENT，工号/手机号→TEACHER，admin→ADMIN
③ BCrypt 校验密码                 →  失败累加计数，达 5 次锁定 15 分钟
④ 签发 JWT（载荷含 userId + role） →  前端落盘 localStorage
⑤ 后续请求带 Authorization: Bearer <token>，由鉴权中间件统一校验
⑥ mustChangePassword=true 时      →  中间件只放行改密白名单，前端路由守卫强制跳改密页
⑦ 改密成功后 token_version + 1    →  旧令牌全部失效，同时回签新令牌
```

### 1.2 JWT 设计

```json
{
  "jti": "be4d71a09669473ba7b46356e3b1d26a",   // 唯一 ID，登出时进黑名单
  "sub": "1",                                  // 用户 ID（需求：token 含用户 ID）
  "iss": "g14-questionnaire",
  "iat": 1792115863,
  "exp": 1792123063,
  "role": "ADMIN",                             // 角色（需求：token 含角色）
  "tv": 0                                      // token_version，令牌版本号
}
```

| 项 | 取值 | 说明 |
|---|---|---|
| 算法 | HS256 | 对称签名，密钥来自 `app.jwt.secret`，长度强制 ≥ 32 字节（`JwtUtil#init` 启动即校验） |
| 有效期 | 7200s（2h） | 可配置 `app.jwt.expire-seconds` |
| 载荷 | 仅 userId / role / tv / jti | **不放姓名、手机号等敏感信息**；载荷只做 Base64Url 编码、未加密 |
| 服务端信任度 | 不信任 `role` | 中间件每次实时查库，以数据库中的角色 / 状态为准 |

### 1.3 账号识别规则

角色一律由后端查库识别，**前端登录页的身份 Tab 只是输入引导，不随请求提交**，防止伪造角色。

| 登录身份 | 账号形态 | 识别依据 |
|---|---|---|
| 学生 | 学号 | `sys_user.account` 命中，`role = STUDENT` |
| 老师 | 工号 | `sys_user.account` 命中，`role = TEACHER` |
| 老师 | 手机号 | 账号未命中且形如 `1[3-9]\d{9}` 时，回落到 `sys_user.phone` 查询；**仅对 TEACHER / ADMIN 开放**（学生必须用学号） |
| 管理员 | admin | `sys_user.account` 命中，`role = ADMIN` |

> 手机号登录时，响应中的 `account` 返回的是**工号**（如 `T1001`）而非手机号，且 `phone` 已脱敏为 `138****0001`。

### 1.4 三层权限模型

权限不是一个开关，而是三层递进，**每一层都必须独立成立**：

| 层 | 解决的问题 | 实现位置 | 失败响应 |
|---|---|---|---|
| ① 认证层 | 是否登录、令牌是否有效 | `AuthInterceptor` 第 4~6 步 | 401 / 40101~40103 |
| ② 角色层 | 这个**角色**能不能调这个接口 | `@RequireRole` + `AuthInterceptor` 第 8 步 | 403 / 40300 |
| ③ 数据层 | 能操作**哪一条**数据 | `PermissionService` | 404 / 40402、40403 |

对应需求 4 的三条规则：

| 规则 | 落点 |
|---|---|
| 老师只能管理自己创建的班级和问卷 | `PermissionService#requireClassVisible` / `#requireQuestionnaireVisible` 判 `teacher_id`、`creator_id` |
| 学生只能查看和填写自己所在班级的问卷 | 同上，判 `class_student` 成员关系 + 问卷 `status=1` |
| 管理员拥有全部权限 | `@RequireRole(allowAdminBypass=true)` + `PermissionService` 中 `isAdmin()` 短路 |

> **关键安全约定**：数据层「不存在」与「越权」返回**完全相同**的响应（同 code、同 message）。
> 若区分 404 与 403，攻击者可用响应差异枚举出系统里存在哪些班级 / 问卷 ID。

### 1.5 令牌失效矩阵（本模块的核心设计）

JWT 天然无状态、签发后无法撤回，但业务上必须支持「登出即失效」「改密即失效」「禁用即踢下线」。
本模块用 **三套机制组合**覆盖全部场景：

| 触发动作 | 机制 | 效果 |
|---|---|---|
| 主动登出 | jti 进内存黑名单 `TokenBlacklist` | 该令牌 401/40103 |
| 修改密码 | `token_version + 1` + 当前 jti 进黑名单 | 该用户**所有设备**的旧令牌 401/40103，同时回签新令牌 |
| 管理员重置密码 | `token_version + 1` | 旧令牌全部 401/40103，且 `must_change_password=1` |
| 管理员禁用账号 | `status = 0` + `token_version + 1` | 在线令牌 403/40301（前端登出回登录页） |
| 令牌自然过期 | JWT `exp` | 401/40100 |

实现要点：中间件每次请求都按 `sub` 实时查库比对 `status` 与 `token_version`，
因此上述变更**立即生效**，无需等待令牌过期。
代价是每请求一次主键查询 —— 单机场景可接受；QPS 上升时把用户状态缓存到 Redis（TTL 30~60s）即可。

## 2. 数据库表结构

完整脚本：`src/main/resources/sql/schema.sql`

### 2.1 sys_user —— 用户表（核心）

```sql
CREATE TABLE `sys_user` (
  `id`                   BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `account`              VARCHAR(64)     NOT NULL COMMENT '登录账号：学生学号 / 老师工号 / 管理员账号',
  `password_hash`        VARCHAR(100)    NOT NULL COMMENT 'bcrypt 密码哈希（$2a$10$...，60 字符）',
  `real_name`            VARCHAR(64)     NOT NULL COMMENT '姓名',
  `role`                 VARCHAR(16)     NOT NULL COMMENT '角色：STUDENT / TEACHER / ADMIN',
  `status`               TINYINT         NOT NULL DEFAULT 1   COMMENT '状态：1=正常 0=禁用',
  `must_change_password` TINYINT         NOT NULL DEFAULT 1   COMMENT '是否需强制改密：1=是 0=否',
  `phone`                VARCHAR(20)     DEFAULT NULL COMMENT '手机号（老师可凭手机号登录）',
  `token_version`        INT             NOT NULL DEFAULT 0   COMMENT '令牌版本号：改密/重置/禁用时 +1',
  `login_fail_count`     INT             NOT NULL DEFAULT 0   COMMENT '连续登录失败次数',
  `locked_until`         DATETIME        DEFAULT NULL COMMENT '锁定截止时间，NULL=未锁定',
  `last_login_time`      DATETIME        DEFAULT NULL COMMENT '最近一次登录成功时间',
  `created_at`           DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`           DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_account` (`account`),
  UNIQUE KEY `uk_phone` (`phone`),
  KEY `idx_role` (`role`),
  KEY `idx_role_status` (`role`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

设计说明（相对需求给出的最小字段集，这里刻意多出的字段及其理由）：

| 字段 | 为什么必须有 |
|---|---|
| `token_version` | 无状态 JWT 的**撤回开关**。没有它，改密 / 重置 / 禁用后旧令牌依然有效到过期，这是最容易漏掉的安全缺口 |
| `must_change_password` | 「首次登录强制改密」的状态位。开通账号置 1，改密成功置 0 |
| `phone` | 支持「老师用手机号登录」；唯一索引防止两个账号绑同一号码 |
| `login_fail_count` / `locked_until` | 防爆破。仅靠前端限流无意义，必须在服务端落库 |
| `real_name` | 需求中的「姓名」。列名用 `real_name` 而非 `name`，避免与保留字和前端 mock 字段混淆 |
| `status` | 逻辑禁用而非物理删除 —— 用户会被班级、问卷、答题记录引用，物理删除会破坏历史数据 |

> `role` 用 `VARCHAR(16)` 存枚举名字符串（而非 `TINYINT`），与前端 `src/utils/role.js` 的
> `STUDENT/TEACHER/ADMIN` 逐字对齐，可读性好且新增角色不需要改数据字典。

### 2.2 其余表

| 表 | 用途 | 关键约束 |
|---|---|---|
| `sys_login_log` | 登录审计（成功/失败、IP、UA、失败原因） | `idx_account_time` 支撑「某账号近期失败记录」排查 |
| `class_info` | 班级（`invite_code` 邀请码、`teacher_id` 属主） | `uk_invite_code` |
| `class_student` | 班级成员（学生加入的班级） | `uk_class_student(class_id, student_id)` 防重复加入 |
| `questionnaire` | 问卷（`class_id`、`creator_id`、`status` 1=已发布 0=草稿） | `idx_class`、`idx_creator` |

后三张表由「班级 / 问卷」模块持有；本模块只读取它们做**数据级权限校验**，
并通过 `/api/permission-demo/*` 演示端点验证规则确实生效。

## 3. RESTful API 列表

### 3.0 统一响应结构

```json
{ "code": 200, "message": "成功", "data": {}, "timestamp": 1792115863000 }
```

- `code` 是**业务码**，成功恒为 `200`（不是 0）；
- HTTP 状态码与业务码同源：`400 ↔ 400xx`、`401 ↔ 401xx`、`403 ↔ 403xx`、`404 ↔ 404xx`、`409 ↔ 409xx`、`500 ↔ 500xx`；
- 前端既能按 HTTP status 粗分流，也能按 `code` 精细提示。

#### ① POST /api/auth/login

请求：

```json
{ "account": "2021001", "password": "Init@1234" }
```

响应 200：

```json
{
  "code": 200,
  "message": "登录成功",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "mustChangePassword": true,
    "user": {
      "id": 4,
      "account": "2021001",
      "realName": "学生一",
      "role": "STUDENT",
      "roleLabel": "学生",
      "status": 1,
      "phone": null,
      "mustChangePassword": true,
      "lastLoginTime": "2026-10-16 10:06:42",
      "createdAt": "2026-10-16 10:06:12"
    }
  },
  "timestamp": 1792115863000
}
```

错误：

| HTTP | code | message | 触发条件 |
|---|---|---|---|
| 401 | 40104 | 账号或密码错误 | 账号不存在**或**密码错误（两者响应完全一致，防账号枚举） |
| 403 | 40301 | 账号已被禁用 | `status = 0` |
| 403 | 40303 | 账号已锁定，请稍后重试 | 连续失败 5 次后 15 分钟内 |

#### ② POST /api/auth/logout

请求体 `{}`。响应 `{ "code": 200, "message": "已登出", "data": null }`。
此后该令牌访问任何接口返回 401 / 40103。

#### ③ GET /api/auth/me

响应 200：`data` 即上文的 `user` 对象（`phone` 已脱敏）。

#### ④ POST /api/auth/password

请求：

```json
{ "oldPassword": "Init@1234", "newPassword": "Student@123" }
```

响应 200：

```json
{
  "code": 200,
  "message": "密码修改成功",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9...(新令牌)",
    "tokenType": "Bearer",
    "expiresIn": 7200,
    "mustChangePassword": false,
    "user": { "...": "..." }
  }
}
```

> **响应必须回签新令牌**：改密让 `token_version + 1`，旧令牌立即失效，
> 前端若继续用旧令牌，下一个请求就会 401/40103。

错误：

| HTTP | code | message | 触发条件 |
|---|---|---|---|
| 400 | 40001 | 密码不符合安全要求（弱口令 / 强度不足） | 长度不在 8~32、缺字母或数字、命中弱口令黑名单 |
| 400 | 40002 | 原密码错误 | `oldPassword` 不匹配 |
| 400 | 40003 | 新密码不能与原密码相同 | `newPassword == oldPassword` |
| 403 | 40302 | 请先修改初始密码 | 处于强制改密状态访问了白名单外的接口 |

#### ⑤ GET /api/auth/teacher-only-demo

响应 200：`data = { message, userId, account, role }`。
学生调用 → 403/40300；未完成改密的老师调用 → 403/40302（强制改密拦截早于角色校验）。

### 3.3 管理端接口

#### ⑥ POST /api/admin/users

请求（`phone` / `initialPassword` 允许显式传 `null`）：

```json
{
  "account": "T1001",
  "realName": "老师甲",
  "role": "TEACHER",
  "phone": "13800000001",
  "initialPassword": null
}
```

- `initialPassword = null` → 使用配置项 `app.auth.initial-password`（`Init@1234`），**只校验长度**；
- `initialPassword` 有值 → 套用**完整**强度策略与弱口令黑名单。

响应 200：`data` 为新建用户的 `UserVO`（含 `id`）。
错误：409/40901 账号已存在、409/40902 手机号已被占用。

> **为什么初始密码走「只校验长度」的宽松分支**：系统初始密码本身就在弱口令黑名单里，
> 对它套用完整策略会自相矛盾（配置说用 `Init@1234`，策略又拒绝 `Init@1234`）。
> 正确的补偿手段是 `must_change_password = 1` —— 用「强制改密」而不是「强度校验」来兜底。

#### ⑦ POST /api/admin/users/{id}/password/reset

请求：`{ "newPassword": "Reset@2024" }`，传 `null` 表示恢复系统初始密码。
响应：`{ "code": 200, "message": "密码已重置", "data": null }`

错误：

| HTTP | code | 说明 |
|---|---|---|
| 404 | 40401 | 用户不存在 |
| 403 | 40304 | 不能重置当前登录的账号（应走「修改密码」接口） |
| 403 | 40305 | 不能重置管理员账号 |
| 400 | 40001 | 显式指定的新密码不合规 |

> **注意方法是 POST，不是 PUT**。用 PUT 调用会得到 400/40000（方法不支持被统一转换）。

#### ⑧ PUT /api/admin/users/{id}/status?enabled=false

开关走 **query 参数**而非请求体。响应 `data` 为更新后的 `UserVO`。
禁用后：该用户在线令牌立即 403/40301，且无法再登录。

#### ⑨ GET /api/admin/users?pageNum=1&pageSize=10&keyword=T1001&role=TEACHER

响应 200：

```json
{
  "code": 200,
  "message": "成功",
  "data": {
    "total": 5,
    "pageNum": 1,
    "pageSize": 10,
    "list": [
      { "id": 2, "account": "T1001", "realName": "老师甲", "role": "TEACHER",
        "roleLabel": "老师", "status": 1, "phone": "138****0001",
        "mustChangePassword": true, "createdAt": "2026-10-16 10:06:12" }
    ]
  }
}
```

- `pageSize` 上限 100，超出会被截断，**并在响应中回显生效值**；
- 列表中的 `phone` 一律脱敏，且不含 `passwordHash` 等内部字段。

## 4. 后端鉴权中间件关键代码

文件：`src/main/java/com/g14/g14/login/security/AuthInterceptor.java`

### 4.1 注册：白名单模式而非黑名单模式

```java
// WebMvcConfig.java
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(authInterceptor)
            .addPathPatterns("/api/**")   // 拦截全部 API
            .order(0);
}
```

> **设计取舍**：采用「默认全部需要鉴权 + 用 `@PublicApi` 显式声明匿名」，
> 而不是维护 `excludePathPatterns` 黑名单。
> 前者在新增接口时**默认是安全的**（忘记加注解只会被拦住，不会裸奔）；
> 后者一旦漏配就会静默产生一个无鉴权接口。

### 4.2 核心链路

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    // 1. 静态资源等非 Controller 请求
    if (!(handler instanceof HandlerMethod)) return true;
    // 2. CORS 预检请求不带 Authorization 头，必须放行
    if (HttpMethod.OPTIONS.matches(request.getMethod())) return true;

    HandlerMethod handlerMethod = (HandlerMethod) handler;

    // 3. 匿名接口（@PublicApi）
    if (isPublicApi(handlerMethod)) return true;

    // 4. 提取并校验 Token
    String token = resolveToken(request);
    if (!StringUtils.hasText(token)) throw new BizException(ResultCode.TOKEN_MISSING);   // 401/40101
    Claims claims = jwtUtil.parse(token);                                               // 401/40100、401/40102

    // 5. 登出黑名单
    String jti = claims.getId();
    if (tokenBlacklist.contains(jti)) throw new BizException(ResultCode.TOKEN_REVOKED); // 401/40103

    // 6. 实时查库：账号存在 → 未被禁用 → 令牌版本一致
    Long userId = jwtUtil.getUserId(claims);
    User user = userMapper.selectById(userId);
    if (user == null) throw new BizException(ResultCode.TOKEN_REVOKED, "用户不存在，请重新登录");
    if (!user.enabled()) throw new BizException(ResultCode.ACCOUNT_DISABLED);            // 403/40301
    if (!Objects.equals(user.getTokenVersion(), jwtUtil.getTokenVersion(claims))) {
        throw new BizException(ResultCode.TOKEN_REVOKED);                               // 401/40103
    }

    // 7. 强制改密拦截
    if (user.requiresPasswordChange() && !inForceChangeWhitelist(request)) {
        throw new BizException(ResultCode.MUST_CHANGE_PASSWORD);                        // 403/40302
    }

    // 8. 角色鉴权
    RequireRole requireRole = resolveRequireRole(handlerMethod);
    if (requireRole != null && !matchRole(requireRole, user.getRole())) {
        throw new BizException(ResultCode.FORBIDDEN);                                   // 403/40300
    }

    // 9. 绑定请求级上下文
    AuthContext.set(LoginUser.of(user, token, jti, jwtUtil.getExpireAtMillis(claims)));
    return true;
}

/** 请求结束务必清理 ThreadLocal，避免 Tomcat 线程复用导致用户身份串号 */
@Override
public void afterCompletion(HttpServletRequest req, HttpServletResponse resp, Object handler, Exception ex) {
    AuthContext.clear();
}
```

**三个容易踩的坑，代码里已针对性处理：**

1. **ThreadLocal 必须清理**。Tomcat 线程是复用的，`afterCompletion` 不 `clear()` 会导致
   下一个请求读到上一个用户的身份 —— 这是最危险的越权漏洞之一，且只在并发下偶发。
2. **403 与 401 不能混用**。账号被禁用返回的是 **403/40301** 而不是 401，
   因为前端对两者的处理不同：401 → 清登录态回登录页；403/40301 → 提示 + 清登录态回登录页；
   403/40300 → 仅提示不跳转（当前页可能只是探测了一个无权接口）。
3. **强制改密拦截必须早于角色校验**。否则处于强制改密态的老师访问老师接口时，
   会先命中角色通过、再被改密拦截 —— 顺序反了会返回错误的错误码。

### 4.3 强制改密白名单

```java
private static final List<String> FORCE_PWD_CHANGE_WHITELIST = Arrays.asList(
        "/api/auth/me",        // 查自己信息
        "/api/auth/password",  // 改密码
        "/api/auth/logout"     // 登出
);
```

> 白名单必须至少包含这三个。少任何一个都会让用户陷入死循环：
> 无法查询自己的状态 → 无法调用改密接口 → 永远卡在 403/40302。

### 4.4 角色注解与匹配

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireRole {
    RoleEnum[] value();
    /** 是否允许管理员直接通过，默认 true —— 对应需求「管理员拥有全部权限」 */
    boolean allowAdminBypass() default true;
}

private boolean matchRole(RequireRole requireRole, RoleEnum actualRole) {
    if (actualRole == null) return false;
    if (requireRole.allowAdminBypass() && actualRole == RoleEnum.ADMIN) return true;
    for (RoleEnum allowed : requireRole.value()) {
        if (allowed == actualRole) return true;
    }
    return false;
}
```

方法级注解优先于类级：

```java
@RestController
@RequestMapping("/api/admin")
@RequireRole(RoleEnum.ADMIN)     // 类级：整个控制器都要管理员
public class AdminController { ... }
```

### 4.5 数据级权限（第二道闸）

角色校验只能保证「学生不能调管理员接口」，但拦不住「老师 A 操作老师 B 的班级」。
后者必须在业务层用**资源属主**判断：

```java
// PermissionService.java
public ClassInfo requireClassVisible(Long classId) {
    LoginUser me = AuthContext.require();
    ClassInfo clazz = permissionMapper.selectClassById(classId);

    if (clazz != null) {
        if (me.isAdmin()) return clazz;                                        // 管理员全放行
        if (me.isTeacher() && Objects.equals(clazz.getTeacherId(), me.getUserId())) return clazz;
        if (me.isStudent() && permissionMapper.countMembership(classId, me.getUserId()) > 0) return clazz;
    }
    // 关键：不存在与越权抛同一个异常 → 响应完全一致，防 ID 枚举
    throw new BizException(ResultCode.CLASS_NOT_FOUND);
}
```

### 4.6 令牌黑名单

```java
// TokenBlacklist.java —— 进程内实现，jti -> 到期时间戳
private final Map<String, Long> store = new ConcurrentHashMap<>();

public void add(String jti, long expireAtMillis) {
    if (expireAtMillis <= System.currentTimeMillis()) return;   // 已过期无需记录
    store.put(jti, expireAtMillis);
}

@Scheduled(fixedDelay = 600_000L)      // 每 10 分钟清理过期条目，防止内存无限增长
public void evictExpired() {
    long now = System.currentTimeMillis();
    store.entrySet().removeIf(e -> e.getValue() <= now);
}
```

> **已知局限**：进程内实现，重启后失效、多实例不共享。
> 生产环境应替换为 Redis：`SETEX blacklist:{jti} <剩余秒数> 1`，
> 并把本类抽象为接口以支持替换。

### 4.7 统一异常出口

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ResponseEntity<Result<Void>> handleBiz(BizException e) {
        ResultCode rc = e.getResultCode();
        return ResponseEntity.status(rc.getHttpStatus())
                .body(Result.fail(rc.getCode(), e.getMessage()));
    }

    /** 方法不支持统一转 400/40000，让前端只需处理一套错误码 */
    @ExceptionHandler(HttpRequestMethodNotSupportedException.class)
    public ResponseEntity<Result<Void>> handleMethodNotSupported(HttpRequestMethodNotSupportedException e) {
        return badRequest("请求方法不支持: " + e.getMethod());
    }
}
```

> 拦截器 `preHandle` 抛出的异常同样会被本处理器捕获（Spring 用 HandlerExceptionResolver 处理），
> 因此鉴权失败返回的是统一 JSON 而不是 Tomcat 默认错误页。

## 5. 前端登录逻辑与路由守卫

前端代码位于 `D:\G14\G14\frontend`，技术栈 Vue 3 + Vue Router 4 + Pinia + Axios + Element Plus。

### 5.1 登录逻辑（`src/views/Login.vue` + `src/stores/auth.js`）

```js
// stores/auth.js —— Pinia action
async login(payload) {
  const res = await apiLogin(payload)              // POST /api/auth/login {account, password}
  const { token, user, mustChangePassword } = res.data
  // 后端 LoginVO 顶层与 user 里都带该标记，统一落到 user 上避免两处不一致
  const merged = { ...(user || {}), mustChangePassword: !!mustChangePassword }
  this.persist(token, merged)                      // 令牌 + 用户信息落 localStorage
  return this.user
}
```

```js
// Login.vue —— 提交后按 mustChangePassword 分流
const user = await authStore.login(form.value)
ElMessage.success('登录成功')
if (user.mustChangePassword) {
  router.replace({ name: 'ForcePassword' })        // 首次登录 → 强制改密页
} else {
  router.replace(route.query.redirect || '/dashboard')
}
```

关键点：

1. **登录请求体只有 `{ account, password }`**，不提交角色 —— 角色由后端查库识别，防止前端伪造；
2. 登录接口带 `skipAuth`，不携带 localStorage 里的旧令牌，避免过期令牌干扰；
3. `utils/user.js` 的 `normalizeUser` 把后端的 `realName` 补齐为页面模板用的 `name`，
   **字段映射只在这一处做**，组件层不感知后端字段名。

### 5.2 路由守卫（`src/router/index.js`）

```js
router.beforeEach(async (to) => {
  const auth = useAuthStore()

  // ① 公开页（登录 / 404）：已登录访问登录页则跳首页
  if (to.meta.public) {
    if (to.name === 'Login' && auth.isLoggedIn) return { name: 'Dashboard' }
    return true
  }

  // ② 未登录 → 登录页，并记录来源以便登录后回跳
  if (!auth.isLoggedIn) {
    return { name: 'Login', query: { redirect: to.fullPath } }
  }

  // ③ 有令牌但无用户信息（刷新页面）：拉一次 /auth/me 恢复会话并顺带校验令牌
  if (!auth.user && auth.token) {
    try {
      await auth.fetchUser()
    } catch (e) {
      auth.logout()
      return { name: 'Login' }
    }
  }

  // ④ 首次登录强制修改初始密码
  if (auth.mustChangePassword && to.name !== 'ForcePassword') {
    return { name: 'ForcePassword' }
  }
  if (to.name === 'ForcePassword' && !auth.mustChangePassword) {
    return { name: 'Dashboard' }          // 已完成改密就别停在改密页
  }

  // ⑤ 角色守卫：路由 meta.roles 未包含当前角色则拒绝
  const roles = to.meta.roles
  if (roles && !roles.includes(auth.role)) {
    return { name: 'Dashboard' }
  }

  return true
})
```

路由表中通过 `meta` 声明权限要求：

```js
{
  path: 'admin/users',
  name: 'AdminUsers',
  component: () => import('../views/admin/UserManage.vue'),
  meta: { title: '账号管理', roles: [ROLE.ADMIN] }     // ← 只有管理员能进
}
```

> **前端守卫不是安全边界**。它只是体验优化（避免用户看到无权页面）。
> 真正的拦截在后端 —— 即使有人手动改 localStorage 里的 role 直接跳 `/admin/users`，
> 页面渲染出来了，但所有 `/api/admin/*` 请求都会被后端 403/40300 拒绝。

### 5.3 响应拦截器（`src/api/request.js`）

401 / 403 必须分流处理，不能一律当「无权限」：

```js
if (status === 401) {
  // 登录接口自己会提示「账号或密码错误」，不能触发全局登出跳转
  if (error.config?.url?.includes('/auth/login')) return Promise.reject(toError(payload))
  handleUnauthorized(payload?.message || '登录已过期，请重新登录')   // 清登录态 → 回登录页
  return Promise.reject(toError(payload))
}

if (status === 403) {
  if (code === 40302) return router.replace({ name: 'ForcePassword' })  // 强制改密 → 跳改密页
  if (code === 40301 || code === 40303) { auth.logout(); return router.replace({ name: 'Login' }) }
  ElMessage.error(payload?.message)                                     // 40300 越权 → 仅提示不跳转
  return Promise.reject(toError(payload))
}
```

| 业务码 | 含义 | 前端行为 |
|---|---|---|
| 40300 | 权限不足 | 仅提示，不跳转 |
| 40301 | 账号已禁用 | 清登录态 → 回登录页 |
| 40302 | 必须修改初始密码 | 跳「修改初始密码」页 |
| 40303 | 账号已锁定 | 清登录态 → 回登录页 |

### 5.4 改密后必须换令牌

```js
// stores/auth.js
async changePassword(payload) {
  const res = await apiChangePassword(payload)     // POST /api/auth/password
  const data = res.data
  if (data && data.token) {
    this.persist(data.token, data.user)            // ★ 必须落盘新令牌
  }
  return res
}
```

> 后端改密让 `token_version + 1`，旧令牌立即失效，同时回签了一个新令牌。
> 前端若不替换本地存储，改密后的下一个请求就会 401/40103 —— 这是联调时最常见的坑。

## 6. 安全设计清单

| 威胁 | 对策 | 实现位置 |
|---|---|---|
| 数据库被拖库后密码泄露 | BCrypt（cost=10，自带随机盐，慢哈希抗爆破） | `PasswordEncoderConfig` |
| 彩虹表 / 相同密码哈希相同 | BCrypt 自带随机盐，同明文每次结果不同 | 同上 |
| 弱口令 | 复杂度（8~32 位含字母数字）+ 弱口令黑名单 | `PasswordPolicy` |
| 账号枚举（凭响应差异猜账号是否存在） | 账号不存在时也执行一次等价耗时的 BCrypt 校验，且响应文案与密码错误完全一致 | `AuthService#login` |
| 暴力破解 | 连续失败 5 次锁定 15 分钟，计数落库 | `AuthService#login` |
| ID 枚举（猜资源 ID） | 越权与不存在返回同码同文案 | `PermissionService` |
| 敏感信息泄漏 | 手机号脱敏、`passwordHash` 加 `@JsonIgnore`、接口只返回 VO | `PhoneMask` / `UserVO` |
| 令牌泄露后长期可用 | 短有效期（2h）+ 改密/禁用即失效（`token_version`） | `JwtUtil` / `AuthInterceptor` |
| 登出后令牌仍可用 | jti 黑名单 | `TokenBlacklist` |
| 前端伪造角色 | 后端查库识别角色，不信任前端提交与令牌载荷中的 role | `AuthService#login` / `AuthInterceptor` |
| 线程复用导致身份串号 | `ThreadLocal` 在 `afterCompletion` 强制清理 | `AuthInterceptor` |
| 管理员互相接管 / 自锁 | 40304 不能操作自己、40305 不能操作管理员 | `AdminService#guardAdminOperation` |
| 新增接口漏加鉴权 | 「默认全部鉴权 + `@PublicApi` 显式放行」的白名单模式 | `WebMvcConfig` |
