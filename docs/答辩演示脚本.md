## 1. 开场（1 分钟，不操作，只讲）

> 这是我们做的校园问卷系统。三种角色：学生填问卷、教师发问卷、管理员管人和审内容。
> 技术栈 Spring Boot 3 + Vue 3，前后端分离，RESTful，数据库 MySQL 8，共 17 张表、72 个接口。
> 演示按验收标准的 AC-01、AC-02、AC-03 走，三条主线各 3 分钟左右。

**要点：先讲「是什么」，不讲「怎么实现」。** 评委对「用了什么框架」的兴趣远低于「能干什么」。

## 2. AC-01 教师主流程（3 分钟）

### 2.1 登录（20 秒）

窗口 1，`teacher` / `Teacher@123` 登录。

**说**：「教师登录后菜单只有我的问卷、模板共享、个人中心——没有用户管理，因为权限码里没有 `user:list`。菜单是根据权限码动态生成的，不是写死的。」

**指给他看**：左侧菜单只有三项。

> 加分点：如果评委追问，可以说「三个角色的权限数分别是 50 / 23 / 10，权限码格式是 `模块:动作:范围`」。

### 2.2 新建问卷 + 出题（60 秒）

1. 「我的问卷」→「新建问卷」
2. 标题填 `课程满意度调查（演示）`，简介一句话，**打开「匿名」开关**，截止时间选明天
3. 保存 → 进入编辑器
4. 加 4 道题：单选（3 选项）、多选（3 选项）、填空、评分题（5 星）
5. 把第 2 题设为必答
6. **刷新页面** → 题目与顺序都在

**说**：「草稿是边编辑边自动保存的，刷新不会丢。刚才这道必答题的开关也存下来了。」

> **别说**「我用的是 MyBatis-Plus 的批量保存」——除非被问到。这里要展示的是「用户视角的可靠性」。

### 2.3 预览（15 秒）

点「预览」→ 学生视角渲染。

**说**：「预览用的是和学生填写页完全同一个组件，所以看到的就是学生看到的。预览不会产生答卷。」

**指给他看**：预览页没有提交按钮 / 提交不产生数据。

### 2.4 发布（20 秒）

点「发布」→ 确认。

**说**：「发布之后题目结构就锁死了。现在再想改题目，系统会提示『问卷已发布，题目结构已锁定；如需调整请复制为新问卷』——这是刻意的。否则一份已经有人填了一半的问卷，题目一改，那些答卷就对不上了。」

**指给他看**：状态变「已发布」、出现 8 位分享码、题干输入框变灰。

> 这是本项目的核心设计决策之一，**必须讲**。评委很吃这种「你考虑到了什么」，而不是「你实现了什么」。

### 2.5 学生填写（40 秒）

切窗口 2（学生已登录），大厅里能看到刚发布的问卷 → 点「去填写」。

答两题 → **直接点提交** → 前端拦下并高亮第 2 题。

**说**：「必答题没填，前端先拦一次，滚动定位到第一道没答的题。后端也会再校验一次——前端校验是为了体验，后端校验是为了正确性，两个都不能省。」

补全 → 提交 → 出现回执（答卷编号 + 提交时间）。

**再进一次这个问卷** → 显示「已提交」，不渲染题目。

**说**：「限填一次的问卷，第二次进来直接显示已提交。这个防线在数据库——`answer_sheet` 上有个唯一索引，两个请求同时提交也只会有一个人成功，另一个人收到 409。」

### 2.6 看统计（30 秒）

切回教师窗口 → 问卷列表 →「统计分析」。

**说**：「这是统计页。单选给了柱状图和饼图两种视角。多选题只给柱状图，因为多选的分母是『这道题有多少人作答』，各选项占比加起来会超过 100%——画成饼图就变成『总共 120%』，是错的。页面上专门有一条提示解释这件事。」

**指给他看**：多选题那块有一条蓝色提示。

> 这条最容易成为答辩追问点。**主动讲清楚「为什么多选不画饼图」，比被问出来强十倍。**

### 2.7 导出（20 秒）

答卷管理 →「导出 Excel」→ 打开文件。

**说**：「两个 Sheet：明细是一行一份答卷、一列一道题；汇总是每道题各选项的人数和占比。**因为这份问卷是匿名的，明细里没有『填写人』和『学号』两列**——匿名不是前端不显示，是后端导出时根本不查这两列。」

### 2.8 暂停（15 秒）

回列表 →「暂停回收」→ 切学生窗口再进该问卷 → 提示已暂停。

**说**：「暂停和结束是两回事：暂停能恢复，结束不能。」

## 3. AC-02 学生主流程（2 分钟）

切窗口 2。

### 3.1 大厅（15 秒）

**说**：「学生登录直接进大厅，只能看到已发布、在时间窗内、并且自己还没填过的问卷。每张卡片上带状态：未开始、进行中、已填写、有草稿。」

### 3.2 断点续答（40 秒）

打开一份问卷 → 答 2 题 → **直接关掉标签页**（真的关掉，别只是切走）。

重新打开 → 进同一份问卷 → 已答内容都在。

**说**：「答题过程中每 5 秒自动存一次草稿，关掉浏览器也不丢。草稿存的是整卷的 JSON，所以答一半也能存——如果拆成明细行存，没答的题就没有行，反而更难还原。」

### 3.3 提交 + 我的记录（30 秒）

补全 → 提交 → 侧边菜单「我的填写记录」。

**说**：「这里能看到我填过的所有问卷、提交时间和答卷状态。**如果是匿名问卷，这里只显示『匿名，不回显』，点不进去看内容**——匿名对填的人自己也是匿名的。」

### 3.4 模板中心评分（35 秒）

侧边菜单 →「模板中心」。

**说**：「这是教师共享出来的问卷模板，只显示审核通过的。学生可以给模板打分，一人一票，再点一次是改分不是加一票。」

点 5 星 → 卡片上的均分立刻变。

**再点 3 星** → 均分变 3.0，但（1 人）不变。

**说**：「人数没变，说明是改分。这条规则在数据库上：`template_rating` 表有个 `(template_id, user_id)` 的唯一索引。」

## 4. AC-03 管理员主流程（3 分钟）

切窗口 3。

### 4.1 全量菜单（15 秒）

**说**：「管理员能看到全部菜单。跟教师比多了用户管理、注册审核、权限配置、模板审核、日志查询、系统配置。」

### 4.2 建教师账号（30 秒）

用户管理 → 新增 → 学工号 `T2024099`、姓名 `演示教师`、角色教师 → 保存。

**说**：「新建的账号带一个『首次登录必须改密』的标记，用默认密码进去第一件事就是改密码。」

> 如果时间紧，这步可以跳过，直接讲下一句。

### 4.3 给学生追加权限（40 秒）

用户管理 → 找到 `student` →「权限」→ 追加 `survey:create` → 保存。

**切窗口 2，刷新** → 学生菜单里出现「我的问卷」。

**说**：「需求里有个『学生干部也能发问卷』。我们的做法不是加一个 `ROLE_STUDENT_LEADER` 角色——那会让权限矩阵从 3 列变成 4 列，而且每个学生干部的权限未必一样。我们是给指定的人追加一条权限，他的角色仍然是学生。生效权限 = 角色权限 ∪ 追加权限，只能加不能减。」

**切回窗口 3** → 撤销这条追加权限 → 切窗口 2 刷新 → 菜单消失。

> 这一段是全项目**最能体现权限设计水平**的地方，30 秒讲完，值得。

### 4.4 禁用账号（30 秒）

用户管理 → 找到学生 → 禁用。

**切窗口 2** → 随便点一个页面 → 请求被拒，跳回登录页。

**说**：「禁用之后，**已经登录的令牌立刻失效**，不需要等它过期。做法是用户表上有个 `token_version`，改密、重置、禁用、删除都会让它 +1，而 JWT 里带着这个版本号，每次请求比对——旧令牌版本号对不上，直接 401。这样不用维护黑名单表，也不用上 Redis。」

> 这也是必讲点。多数课程项目讲「JWT 无状态」但答不出「怎么让令牌提前失效」。

### 4.5 模板审核（40 秒）

模板审核 →「查看内容」抽屉 → 驳回，原因填 `题目表述有歧义`。

**切窗口 1（教师）→ 我共享的模板** → 看到驳回原因 →「重新提交」。

**切回窗口 3** → 审核通过。

**切窗口 2（学生）→ 模板中心** → 这个模板出现了。

**说**：「驳回必须填原因，不填提交不了——因为作者要知道改哪里。重新提交后旧的驳回意见会自动清空，不会残留。」

### 4.6 日志（25 秒）

日志查询。

**说**：「刚才这些操作全在这里：登录、禁用、审核、导出。**页面上没有任何删除按钮**——日志只增不改是需求，不是没做完。真实失败原因只写进日志（比如『账号不存在』），返回给用户的一律是『账号或密码错误』，防账号枚举。」

### 4.7 尝试禁用自己（15 秒）

用户管理 → 找到自己的账号 → 禁用 → 被拒。

**说**：「不能禁用自己，也不能删掉最后一个管理员，否则系统就没人管了。」

### 4.8 系统配置（30 秒）

系统配置 → 改站点名 → 保存。

**指给他看**：侧边栏品牌、浏览器标签、**退出登录后的登录页**三处都变了。

**说**：「站点名不是写死在前端的，是登录前从公开配置接口拿的——所以未登录的登录页也能显示正确的站点名。这个接口不需要令牌，因为它返回的只有站点名、公告和密码规则，不含任何敏感项。」

再改密码最小长度 → 12 → 保存 → 切到注册页 → 提示同步变成「12~32 位」。

**说**：「密码规则也是配置。之前前端把『8~32 位』写死在提示里和校验里，管理员一改配置，界面提示就跟实际规则打架了。现在文案和校验都读同一份配置。」

## 5. 收尾（1 分钟，回到 PPT）

四个要点，各一句话：

1. **两个硬指标有报告，不是口头保证**。100 并发 5 分钟，提交 P95 640ms、平均 495ms，故障率 0，答卷数 44405 = 成功提交数 44405，零死锁。报告在 `docs/test/压测报告.md`。
2. **性能问题是查出来的，不是猜出来的**。我们做了数据库层基准测试，发现单次 commit 要等一次磁盘 fsync、吞吐锁死在 170 次/秒，而一次提交原本要付 3 次 commit——合并成 1 次后 P95 首次达标。
3. **死锁是结构性消除的，不是靠重试兜住的**。重试能让 500 消失、指标达标，但 MySQL 的死锁日志还在继续增长。验收条件写的是「无死锁日志」而不是「无 500」，就是为了防这一手。
4. **测试是 955 条自动化断言**：后端接口 711 条、前端 E2E 200 条、单元测试 34 条、性能与长稳 10 条判定，全绿。

## 6. 追问准备（评委最可能问的 10 个问题）

### Q1「为什么统计不做预聚合表？」

预聚合会引入「答卷提交了但统计没变」的窗口，还得在提交、标记无效、恢复、删除四条路径上都触发重算，任何一条漏了就是数据不一致。课程级数据量下现算一次不到 100ms，不值得。**判断标准是数据量，不是技术炫技。**

### Q2「多个学生同时提交同一份限填一次的问卷，会怎样？」

只会有一个人成功。`answer_sheet` 上有个 STORED 生成列 `uniq_user = CASE WHEN limit_once=1 AND deleted=0 THEN user_id ELSE NULL END`，唯一索引挂在 `(survey_id, uniq_user)`。限填一次的问卷 `uniq_user` 就是 user_id，第二次必撞；可重复填写的问卷 `uniq_user` 是 NULL，MySQL 允许多个 NULL，所以能无限次提交。**一套索引同时满足两种语义**——如果直接给 `(survey_id, user_id)` 建唯一索引，可重复填写的问卷就彻底不能用了。

### Q3「限定一次如果只在前端拦，或者只在后端『先查一下有没有』呢？」

压测里实测过：10 个并发首存草稿时有 10 个 500。「先查再插」在并发下两个请求会同时判断为「不存在」。而且即使 catch 了唯一键冲突再重查也不行——MySQL 默认 REPEATABLE READ，本事务的快照建立于对方提交之前，重新查还是看不到那行。最后改成 `INSERT ... ON DUPLICATE KEY UPDATE` 一条语句搞定。

### Q4「匿名问卷，后端到底存不存填写人？」

存。`answer_sheet.user_id` 一直有值，因为要用它做限填一次和「我的填写记录」。裁剪发生在**出口**：查答卷的接口在匿名时把 `userId` / `fillerName` / `fillerUsername` 全部置 null，导出时直接不查这两列。这样库里数据是完整的（出问题能追），但任何一个 API 都拿不到。**匿名 ≠ 不存，匿名 = 不返回。**

### Q5「JWT 怎么做到提前失效？」

用户表有 `token_version`。JWT 里带这个数字，每次请求从库里读当前值比对。改密、重置、禁用、删除时 +1，旧令牌立刻对不上。不需要黑名单表，也不需要 Redis。代价是每个请求多一次查库——那个查询本来就要查用户状态，顺手带出来。

### Q6「权限是怎么校验的？会不会有漏的地方？」

三层，缺一不可：方法级 `@RequirePerm`（这个接口要什么权限）、视角级（同一个列表接口，`scope=mine/audit/browse` 是三种不同的人看三种不同的数据，服务层再校验一次）、数据级（`requireOwned` 判断这条记录是不是你的）。

特别说明：**模板没有 `*:all` 全量权限**，管理员也不能下架或删除别人的模板。因为模板是教师自己的作品，管理员只有审核权。

### Q7「多选的占比为什么会超过 100%？是不是算错了？」

没算错。分母是「这道题有多少人作答」，不是「所有选项被选次数之和」。5 个人里 4 个选了 A，A 就是 80%；如果还有 4 个选了 B，B 也是 80%，两个加起来 160%——这是正确的，因为这两个人是同一批人。所以多选不能画饼图，画出来是「总共 160%」。页面上有提示。

### Q8「出了 500 怎么排查？」

统一异常处理会把堆栈写进 `app.log`，返回给前端的是中文提示 + 稳定的业务码。日志里有完整的请求路径、用户、参数摘要。我们没有把堆栈返给前端——那等于把表结构和依赖版本告诉攻击者。

### Q9「如果要做 1000 并发呢？」

现在 100 并发时 Hikari 连接池是 20、MySQL `max_connections` 是 151，先到瓶颈的会是这两处。往上的路径是：连接池按核数调、读写分离、提交路径改成异步落库（先写消息队列再入库）、`answer_count` 这类热点行改成 Redis 计数器定期回写。但**这些都不该在课程项目里做**——没有真实流量，加了只是增加复杂度和出错面。

### Q10「docker-compose 验证过吗？」

验证过，而且验证过程本身发现了 6 个只在全新部署时才暴露的缺陷，都修了：
漏挂 `05_schema_config.sql`（新部署没有配置表，系统配置页直接 500）、
`05` 脚本缺 `USE`（MySQL 初始化报 1046，整站起不来）、
容器里中文双重编码（客户端字符集退回 latin1，中文全变 `æ ¡å›­`）、
`APP_JWT_SECRET` 环境变量实际不生效（yml 里是纯字面量，Spring 不会覆盖）、
nginx 只监听 IPv4 导致容器一直 unhealthy（`localhost` 解析到 `::1`）、
`/v3/api-docs` 被 SPA 的 `try_files` 回落成 200 + 首页。

`docker compose up -d --build` 通过，三容器 healthy，经 nginx 把登录/建卷/发布/填写/统计/导出/模板/审核/日志/配置全链路走了一遍。

需要如实说明的边界：这是在**本机 Windows + Docker Desktop（Linux 容器）**上验证的，没在真实云服务器上跑过；云上还要自己处理安全组放行、ICP 备案和 HTTPS 证书。部署步骤写在 `docs/deploy/部署文档.md`。

> **这条一定要如实说。** 说「验证过」然后被要求现场跑，是最难看的场面。

| 打开 DevTools 讲实现 | 评委看不懂，且占时间 |
| 说「这个功能还没做完」 | 改成「这个是 P2，我们明确不做，原因是……」（都有文档支撑） |
| 逐页翻 PPT 念文字 | PPT 只放图和数据，话在人嘴里 |
| 主动交代「云服务器上还没实际部署过」 | 讲清哪些验证过、哪些没验证，比被问出来强 |
