# 密码找回接口（密保问题）

> 对应需求：`docs/requirements/SRS-需求规格说明书.md` 4.1 认证域（登录 / 安全管理）
> 实现：`backend/src/main/java/com/yjh/backend1/module/recovery/`
> 数据表：`sys_user_recovery`、`sys_recovery_log`（见 `deploy/sql/06_schema_recovery.sql`）
> 配置项：`security.recovery.enabled` / `security.recovery.max-fail` / `security.recovery.lock-minutes`

---

## 1. 为什么是密保问题

最初考虑的四个通道：

| 方案 | 结论 |
|---|---|
| 邮箱验证码 | 排除。工程里没有 SMTP 依赖，学校邮箱也不保证人人可用 |
| 短信验证码 | 排除。要买短信网关 + 报备模板，审核 1~2 天，课程项目扛不住 |
| 只做管理员重置 | 排除。这不是「找回」，是「找人」；晚上十一点忘了密码没人给你重置 |
| **密保问题** | **采用**。零外部依赖、零成本、用户自己就能走完 |

密保问题的固有弱点是「答案可能被别人猜到」（学号、生日、宿舍号在班级群里都是公开的）。所以整套设计的重点不是把问题设计得多巧妙，而是**让猜的成本可计量、可拦截、可追溯**：

- 答案 **BCrypt 哈希存储**，数据库泄露也拿不到原文
- 连续答错 **锁定**，次数与时长由管理员配置（默认 5 次 / 30 分钟）
- 每次尝试写 `sys_recovery_log`，谁在什么 IP 试过谁的账号一目了然
- 失败计数**独立于登录失败计数**（详见 §6.2）

## 2. 数据模型

```
sys_user_recovery                        -- 一个用户至多一条
  user_id          BIGINT   UNIQUE uk_user
  question1        VARCHAR(120)           -- 题目文本，明文存
  answer_hash1     VARCHAR(100)           -- BCrypt(归一化后的答案)
  question2        VARCHAR(120)
  answer_hash2     VARCHAR(100)
  fail_count       INT                     -- 连续错误次数，答对清零
  locked_until     DATETIME  NULL          -- 锁定到期时间
  last_verify_time DATETIME  NULL
  create_time / update_time
  KEY idx_locked (locked_until)

sys_recovery_log                         -- 只增不改
  id / user_id / username
  step      VARCHAR(16)  LOOKUP / VERIFY / RESET
  result    TINYINT      1 成功 0 失败
  reason    VARCHAR(255)
  ip        VARCHAR(64)
  create_time
  KEY idx_username_time (username, create_time)
  KEY idx_user_time     (user_id, create_time)
  KEY idx_result_time   (result, create_time)
```

### 2.1 为什么不往 `sys_user` 加列

`sys_user` 是最热的表（每次鉴权都要读），而密保是「设置一次、一年用一次」的字段。把 `question1/answer_hash1/...` 五列塞进去，等于让每一次登录查询都多拖五列从来没被用到的数据。

独立成表还有一个附带好处：**「有没有设置密保」变成一个 `EXISTS` 判断**，而不是判断某个列是不是 NULL。

### 2.2 为什么题目明文存、答案哈希存

- **题目必须明文**：它要显示给用户看（「我当年设的是什么问题来着」）。题目本身不含隐私。
- **答案必须哈希**：学号、母亲姓名、宿舍号在班级群里都是公开信息，明文存储等于「每个设置了密保的账号都配了第二把挂在门口的钥匙」。用 BCrypt 与登录密码同一个编码器（cost=10），不需要额外依赖。

代价是「管理员也看不到答案」，所以用户连答案都忘了时，只能走 `DELETE /api/users/{id}/recovery` 清掉重设（见 §4.6）。这个代价是必须付的。

### 2.3 为什么不预设问题字典

常见做法是给一张 `recovery_question` 字典表 + 下拉选择。否决理由：字典表会限制住最有效的那些题——「我的宿舍号是多少」「我小学班主任姓什么」这类**只有本人答得上来的题，恰恰是自由输入才写得出来的**。给一个下拉框，用户只能在「我母亲的姓名」和「我的出生城市」里选，而这两个在社交网络上都能查到。

所以题目是自由文本，前端给四个**可点击的预设**（点一下填进输入框，之后还能改）作为引导，而不是限制。

## 3. 接口清单

| # | 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|---|
| 1 | POST | `/api/auth/recovery/lookup` | **免登录** | 用账号换回两个密保问题 |
| 2 | POST | `/api/auth/recovery/reset` | **免登录** | 答题 + 设新密码 |
| 3 | GET | `/api/auth/recovery/mine` | 需登录 | 当前用户是否已设密保 |
| 4 | GET | `/api/auth/recovery/my-questions` | 需登录 | 当前用户的题面（改密保时回显） |
| 5 | PUT | `/api/auth/recovery/setup` | 需登录 | 设置 / 覆盖密保问题 |
| 6 | DELETE | `/api/users/{id}/recovery` | `user:reset-password` | 管理员清除某用户的密保 |

前两个接口在 `AuthInterceptor.WHITE_LIST` 里。**免登录不等于不防护** —— 完整的失败计数、锁定与流水记录都在 Service 内部，见 §6。

## 4. 逐接口说明

### 4.1 `POST /api/auth/recovery/lookup`

请求：

```json
{ "username": "20241001" }
```

响应 `data`：

```json
{ "username": "20241001", "question1": "我的宿舍号是多少？", "question2": "我母亲的姓名是？" }
```

**刻意不返回 `userId`**。若返回了，前端就有可能被改造成「直接提交 userId + 答案」去改某个人的密码，等于把「必须先知道账号」这道门拆掉。

三种失败都返回 404 / 403 / 409 而不是统一文案，因为**下一步动作不同**：

| 情况 | 状态码 | 文案 |
|---|---|---|
| 账号不存在 | 404 | 该学号/工号不存在，请核对后重试 |
| 账号被禁用 | 403 | 该账号已被禁用，无法自助找回，请联系管理员 |
| 注册后未通过审核 | 403 | 该账号尚未通过审核，暂不支持自助找回 |
| 没设置密保 | 404 | 该账号还没有设置密保问题，请联系管理员重置密码 |
| 已锁定 | 409 | 密保验证失败次数过多，请 N 分钟后再试 |
| 管理员关闭了自助找回 | 403 | 管理员已关闭自助找回密码，请联系老师或管理员重置 |

这确实泄露了「这个账号存在」。但换来的题面对攻击者没有额外价值（题面本来就要给人看），而把六种情况合并成一句「账号或密保信息有误」，只会让真正的用户在「是我记错账号了？还是我没设过密保？」之间反复试，最后变成一次失败尝试。

### 4.2 `POST /api/auth/recovery/reset`

请求：

```json
{
  "username": "20241001",
  "answer1": "A-312",
  "answer2": "王秀兰",
  "newPassword": "NewPass@2026"
}
```

响应：`{"code":200,"msg":"密码已重置，请用新密码登录"}`

校验顺序（**顺序本身是设计**）：

1. 账号存在性 → 404（不存在时也跑一次 BCrypt 比对 `DUMMY_HASH`，抹平耗时差异）
2. 账号状态 → 403
3. 是否设置了密保 → 404
4. **是否锁定 → 409（放在验答案之前）**
5. 两个答案都对 → 否则 `recordFailure` 并抛 400 / 409
6. 新密码合规（走 `PasswordPolicy.check(pwd, configService.passwordRules())`）
7. 新密码不能与原密码相同 → 400
8. 写库（`applyReset`）
9. 写 `sys_recovery_log` + 操作日志

第 4 步在验答案之前，是因为锁定期间不该白跑两次 BCrypt（一次 10ms 量级，攻击者可以靠这个把 CPU 打满）。第 6 步在计数之后，是因为「密码太弱」不是「答案错了」，不该消耗尝试次数——但它必须在验答案**之后**，否则就成了一个免费的密码规则探测器。

### 4.3 `GET /api/auth/recovery/mine`

响应 `data`：`true` / `false`。

个人资料页用它决定按钮文案是「设置密保」还是「修改密保」。

### 4.4 `GET /api/auth/recovery/my-questions`

响应 `data` 同 §4.1，但**只返回自己的**。用途：改密保时把题面回显出来，答案框留空（服务端只有哈希，回显不出原文，也不需要）。

### 4.5 `PUT /api/auth/recovery/setup`

请求：

```json
{
  "items": [
    { "question": "我的宿舍号是多少？", "answer": "A-312" },
    { "question": "我母亲的姓名是？", "answer": "王秀兰" }
  ]
}
```

响应：`{"code":200,"msg":"密保问题已保存"}`

**用对象包一层 `items` 而不是裸数组**：Spring 对「请求体直接是 List」的元素级 `@Valid` 不级联，裸数组的 `@NotBlank` 会静默失效。这是本项目踩过的老坑（`QuestionBatchSaveRequest`、`ConfigSaveRequest` 同理）。

校验与归一化：

- 恰好 2 个（`@Size(min=2,max=2)`）
- 题目不能为空、不能相同（忽略大小写与首尾空格）
- 答案不能相同、长度 ≥2
- 题目长度 ≤120

答案在存库前做 `normalizeAnswer`：**全角 ASCII（`\uFF01`–`\uFF5E`）转半角、`\u3000` 转空格、trim、转小写**。中文不受影响；英文答案若区分大小写，会让用户在心里想对了的情况下仍被锁 30 分钟——那是产品缺陷，不是安全特性。

保存会**完全覆盖**旧密保并清零 `fail_count` / `locked_until`。已设置过的用户界面上有明确提示「原来的答案无法回显，保存后会完全覆盖」。

### 4.6 `DELETE /api/users/{id}/recovery`

权限：`user:reset-password`（复用，不新开权限码——语义都是「帮这个人重新拿到账号」）

响应：`{"code":200,"msg":"已清除该用户的密保问题，请通知其登录后重新设置"}`

**清除而不是只解锁**：这是本功能唯一的「真人兜底」。用户连答案都忘了时，重置密码只能让他登进来，找回通道依然是堵的；而且如果只解锁不解绑，他下次再忘时照样卡在同一套答不上的题上。既然是「帮到底」，就把密保一起清掉，让他登录后重设。

失败分支：用户不存在 404 / 该用户没设密保 400。

前端入口在用户管理页操作列的「更多 → 清除密保」。

## 5. 状态与流转

```
未设置 ──(setup)──► 已设置 ──(答对全部)──► 已重置（fail_count=0，密码已换）
                      │
                      ├──(答错)──► fail_count + 1
                      │              └──(达到上限)──► 锁定 30 分钟
                      │                                    │
                      └──────────(重新 setup)──────────────┘
                                   失败累计被清零

锁定中 ──(管理员 clear)──► 未设置（fail_count=0, locked_until=NULL）
```

## 6. 关键设计

### 6.1 失败计数必须写在独立事务里（本项目踩过的真缺陷）

第一版 `reset` 方法上挂了 `@Transactional`，失败路径直接 `throw BizException.badRequest(...)`。表面完全正常——错误提示文案是对的——但 `fail_count` **永远是 0**：`BizException` 是 `RuntimeException`，抛出即触发整个事务回滚，刚写入的计数一起被撤销了。防爆破形同虚设，而且是那种「不打日志、不报错、只在压测时才被发现」的缺陷。

修法是把「必须留下来的写操作」搬到**另一个 Bean**：

```
RecoveryWriteService.recordFailure(...)   @Transactional(propagation = REQUIRES_NEW)
RecoveryService.reset(...)                不加 @Transactional
```

`REQUIRES_NEW` 让它开一个独立事务，外层抛异常不影响它已提交的结果。而 `RecoveryService.reset` 之所以**不能**加 `@Transactional`：一旦外层包了事务，独立事务虽已提交，但外层回滚时……更关键的是，包了事务后整个方法就变成一个「要么全成、要么全不成」的单元，而「记一次失败」这件事的业务语义恰恰是「即使失败也要留下痕迹」。

这也是为什么这两个方法必须在不同类里——Spring 声明式事务基于代理，**同类内部调用不经过代理，`REQUIRES_NEW` 完全不生效**。

### 6.2 失败计数为什么不复用 `sys_user.login_fail_count`

因为那两个计数器回答的是不同的问题：

- `login_fail_count`：这个人**自己**记不住密码
- `sys_user_recovery.fail_count`：有人**拿着他的账号**在试密保答案

混在一起会出大事——同学之间互相知道学号，有人拿别人的学号乱试密保，会把那个人正常登录也一起锁掉。这就是一次「低成本 DoS」：攻击者不需要知道密码，只要有学号列表。

所以两套计数完全独立，`smoke_recovery.ps1` 第 11 组专门断言这一点：密保锁定时，`POST /api/auth/login` 依然 200。

### 6.3 锁定期间为什么要拒绝正确答案

直觉上「答对了就放行」更友好，但那会让锁定毫无意义：攻击者在锁定期间继续爆破，只要有一次答对就进去了，锁定只挡住了不会算的人。

所以锁定就是锁定，正确答案也拒。用户看到的是「密保验证失败次数过多，请 30 分钟后再试」，管理员可以立刻清除解封（§4.6）。

### 6.4 为什么不发「临时票据」

常见设计是：第一步验证账号通过后发一个短时效 token，第二步拿 token + 答案去重置。这样第二步不用重复传 username。

否决理由：**题面本身就是公开的**——任何知道学号的人都能 `lookup` 拿到题面。票据能保护的信息量约等于零，却要多一个存储、过期时间、防重放校验。而重置成功与否，取决于答案对不对，跟「第一步有没有通过」无关。

省掉票据后，`reset` 就是一个完全幂等的接口：给定 username + 两个正确答案 + 合规新密码，结果恒定。

### 6.5 密码策略跟系统配置走，不写死

`RecoveryResetRequest.newPassword` 只写 `@Size(max=64)`，**不写 min、不写复杂度**。原因见 `docs/api/系统配置接口.md` §5：DTO 里写死 `@Size(min=8,max=32)` 会让「管理员把最小长度调到 12」之后，接口仍报「8~32 位」，文案与配置对不上。

真正的强度校验统一走 `PasswordPolicy.check(pwd, configService.passwordRules())`。

### 6.6 整个模块的两个超时/上限都 clamp 而不报错

`maxFail()` clamp 到 3~10，`lockMinutes()` clamp 到 5~1440。管理员如果把 `max-fail` 写成 0 或者 10000，系统不会拒绝启动、也不会报错，而是按边界值工作。理由同 `ConfigService.passwordRules()`：**把人锁在门外的配置错误，不该让管理员连修配置的入口都进不去**。

## 7. 错误码速查

| 状态码 | 场景 |
|---|---|
| 400 | 答案为空 / 两问相同 / 两答相同 / 答案少于 2 字 / 新密码不合规 / 新密码与原密码相同 |
| 400 | 密保答案不正确，还可尝试 N 次（N>0 时一律 400，不是 401） |
| 400 | 该用户没有设置密保问题（管理员清除时） |
| 400 | 必须设置 2 个密保问题 / 密保问题超过 120 字 |
| 401 | 未登录却调 `/mine`、`/my-questions`、`/setup` |
| 403 | 账号被禁用 / 未通过审核 / 管理员关闭了自助找回 |
| 404 | 账号不存在 / 没设置密保 / 管理员清除时用户不存在 |
| 409 | 已锁定；或本次答错正好触发锁定 |

**注意「答案错误」用 400 不用 401**：401 在本项目里语义固定为「令牌缺失或失效」，前端拦截器收到 401 会直接跳登录页。答案错误如果也返 401，用户会被莫名其妙踢回登录页——而他正在找回密码，本来就没登录。

## 9. 已知限制

1. **密保问题可能被人猜到**。学号、生日、宿舍号在同学之间都不是秘密。这是密保问题这个方案固有的弱点，缓解手段是失败计数 + 锁定 + 流水，而不是「设计更巧妙的问题」。
2. **答错不影响登录**（§6.2），所以「有人试你的密保」不会给你任何提示。只有管理员查 `sys_recovery_log` 才看得到。若要做成「连续失败若干次后通知本人」，需要一个通知通道——本项目没有。
3. **管理员清除没有二次确认的后端强制**。清除是高危操作（等于解绑第二把钥匙），但权限复用 `user:reset-password`，持有该权限的人可以直接清。前端有确认框，后端没有额外要求（例如要求管理员输入自己的密码）。在课程项目的信任模型下可以接受，生产环境应该补。
