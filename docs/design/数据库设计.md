| 分组 | 表 | 用途 |
|---|---|---|
| 认证与权限（8） | `sys_user` `sys_role` `sys_permission` `sys_user_role` `sys_role_permission` `sys_user_permission` `sys_login_log` `sys_operation_log` | 账号、RBAC、审计日志 |

ER 图见 `docs/design/erd/`：`er_auth.png`（认证权限）、`er_survey.png`（问卷答题）、`er_answer.png`（答卷明细）、`er_overview.png`（全局）。

### 1.1 关系

```
sys_user 1──n sys_user_role n──1 sys_role 1──n sys_role_permission n──1 sys_permission
sys_user 1──n sys_user_permission n──1 sys_permission          （追加权限，只加不减）
sys_user 1──n sys_login_log / sys_operation_log                （日志不设外键，见 3.6）

sys_user 1──n survey 1──n survey_question 1──n survey_question_option
sys_user 1──n survey_template 1──n template_rating
survey   1──n answer_sheet 1──n answer_item
survey   1──n survey_draft

survey_template ... source_survey_id → survey                 （仅追溯，无外键）
```

### 1.2 三条全局约定

**约定 A：业务主表用逻辑删除，日志表与关联表不用。**

有 `deleted` 的表：`sys_user` `survey` `answer_sheet` `survey_template` `sys_config`。
没有 `deleted` 的表：`survey_question` `survey_question_option` `survey_draft` `template_rating` `sys_login_log` `sys_operation_log` `sys_*_role` `sys_*_permission`。
理由各不相同，见第 5 节「关键设计决策」。

**约定 B：`create_time` / `update_time` 由数据库默认值兜底，业务代码也会写。**

DDL 里是 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`，同时 MyBatis-Plus 的 `MetaObjectHandler` 也会填。双保险的原因：手工执行 SQL 修数据时不用手动填时间，而走应用时能得到精确的实体时间。

**约定 C：不使用数据库外键约束。**

课程级项目里外键会让「清理测试数据」变成一场顺序游戏（必须先删子表再删父表，顺序错了就报 1451）。改用应用层校验 + 索引保证查询性能。代价是可能出现孤儿行，因此 `deploy/sql/90_cleanup_test_data.sql` 严格按子→父顺序删除。

## 2. 认证与权限（8 张）

### 2.1 sys_user — 用户表

| 字段 | 类型 | 空 | 默认 | 键 | 说明 |
|---|---|---|---|---|---|
| id | bigint unsigned | NO | auto | PK | 主键 |
| username | varchar(64) | NO | — | UNI | 登录账号：学号/工号/管理员账号 |
| password_hash | varchar(100) | NO | — | | BCrypt 哈希（`$2a$10$...`，60 字符，留余量） |
| real_name | varchar(64) | NO | — | | 姓名 |
| status | tinyint | NO | 1 | MUL | 1=正常 0=禁用 |
| audit_status | tinyint | NO | 1 | MUL | 0=待审核 1=已通过 2=已驳回 |
| must_change_password | tinyint | NO | 0 | | 1=下次登录强制改密 |
| phone | varchar(20) | YES | NULL | MUL | 手机号 |
| email | varchar(128) | YES | NULL | | 邮箱 |
| department | varchar(128) | YES | NULL | | 院系/班级 |
| token_version | int | NO | 0 | | 令牌版本，改密/重置/禁用时 +1 |
| login_fail_count | int | NO | 0 | | 连续登录失败次数 |
| locked_until | datetime | YES | NULL | | 锁定截止时间 |
| last_login_time | datetime | YES | NULL | | 最近登录成功时间 |
| audit_remark | varchar(255) | YES | NULL | | 审核意见（驳回原因） |
| remark | varchar(255) | YES | NULL | | 备注 |
| deleted | tinyint | NO | 0 | | 逻辑删除 |
| create_by / create_time / update_by / update_time | | | | | 审计字段 |

索引：`uk_username(username)`、`idx_status(status,deleted)`、`idx_audit(audit_status,deleted)`、`idx_phone(phone)`。

**`token_version` 是本节最重要的一个字段**。JWT 无状态，签出去就没法收回；把版本号写进令牌声明（`ver`），每次鉴权时比对数据库。改密、管理员重置密码、禁用、删除账号时 `token_version + 1`，旧令牌立刻失效——不需要维护黑名单表，也不需要 Redis。

### 2.2 sys_role / sys_permission — 角色与权限字典

`sys_role`：`id` / `code`（`uk_code`）/ `name` / `description` / `builtin`（1=内置不可删）/ `create_time`。三条内置：`ROLE_ADMIN` `ROLE_TEACHER` `ROLE_STUDENT`。

`sys_permission`：`id` / `code`（`uk_code`）/ `name` / `module`（`idx_module`）/ `description` / `create_time`。共 50 条，格式 `模块:动作[:范围]`，例如 `survey:update:self`、`answer:read:survey:all`。

### 2.3 三张关联表

| 表 | 字段 | 唯一键 |
|---|---|---|
| sys_user_role | id / user_id / role_id / create_by / create_time | `uk_user_role(user_id, role_id)` |
| sys_role_permission | id / role_id / perm_id / create_time | `uk_role_perm(role_id, perm_id)` |
| sys_user_permission | id / user_id / perm_id / grant_by / grant_time / remark | `uk_user_perm(user_id, perm_id)` |

**`sys_user_permission` 的存在理由**：需求里「学生干部可以发问卷」，但如果为此新增 `ROLE_STUDENT_LEADER`，权限矩阵会从 3 列变 4 列，而且每个学生干部的权限未必相同。改成「给指定用户追加一条权限」，角色仍是 `ROLE_STUDENT`。生效权限 = 角色权限 ∪ 追加权限（只加不减）。

### 2.4 sys_login_log / sys_operation_log — 日志

`sys_login_log`：`id` / `user_id`（可空，账号不存在时为 NULL）/ `username`（`idx_username_time`）/ `result`（1成功 0失败）/ `reason` / `ip` / `user_agent` / `create_time`（`idx_time`）。

`sys_operation_log`：`id` / `user_id` / `username` / `module`（`idx_module_time`）/ `action` / `target_type` / `target_id` / `detail`（脱敏后，≤1000）/ `result` / `ip` / `create_time`。

**两张日志表都没有 `deleted`、没有 `update_time`**。日志只增不改（FR-LOG-03），给了 `deleted` 就等于给了「悄悄删证据」的入口。

## 3. 问卷（3 张）

### 3.1 survey — 问卷主表

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| id | bigint unsigned | auto | PK |
| title | varchar(120) | — | 标题 |
| description | varchar(1000) | NULL | 简介/填写说明 |
| category | varchar(32) | `OTHER` | TEACHING / ACTIVITY / SATISFACTION / OTHER |
| anonymous | tinyint | 0 | 1=匿名 |
| status | varchar(16) | `DRAFT` | DRAFT / PUBLISHED / PAUSED / CLOSED |
| share_code | varchar(16) | NULL | 8 位分享码，全局唯一 |
| start_time | datetime | NULL | NULL=立即开始 |
| end_time | datetime | NULL | NULL=长期有效 |
| limit_once | tinyint | 1 | 1=每人一份 |
| question_count | int | 0 | 冗余题量 |
| answer_count | int | 0 | 冗余回收量（**= 有效答卷数**） |
| published_time / closed_time | datetime | NULL | 首次发布 / 人为结束时刻 |
| create_by / create_time / update_by / update_time / deleted | | | 审计 + 逻辑删除 |

索引：`uk_share_code(share_code)`、`idx_owner(create_by,status,deleted)`、`idx_status_time(status,end_time)`、`idx_create_time`、`idx_title`。

### 3.2 survey_question / survey_question_option

`survey_question`：`id` / `survey_id` / `question_type`（SINGLE / MULTIPLE / TEXT / TEXTAREA / RATING）/ `title`(255) / `description`(500) / `is_required` / `max_length` / `rating_max` / `sort_no` / 审计字段。索引 `idx_survey_sort(survey_id,sort_no)`。

`survey_question_option`：`id` / `question_id` / `survey_id`（冗余）/ `content`(255) / `sort_no` / `create_time`。索引 `idx_question_sort(question_id,sort_no)`、`idx_survey(survey_id)`。

两张子表**没有 `deleted`**：题目只在 DRAFT 阶段可改，草稿没有答卷，删掉就是脏数据而不是需要追溯的历史。保留逻辑删除反而会让「整卷差量保存」多一层过滤。

### 3.3 status 里没有 DELETED

SRS 状态机写了 `DRAFT→PUBLISHED⇄PAUSED→CLOSED→DELETED`。库里 `status` 不存 `DELETED`，删除由 `deleted=1` 表达。

如果两处都存，就会出现「status=CLOSED 但 deleted=1」「status=DELETED 但 deleted=0」这类需要人工判断谁更权威的矛盾数据。接口层永远不返回 `DELETED`，语义等价于 `deleted=1`。

## 4. 答题（3 张）

### 4.1 answer_sheet — 答卷头

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint unsigned | PK，同时作为答卷编号对外展示 |
| survey_id | bigint unsigned | 所属问卷 |
| user_id | bigint unsigned | 填写人。**匿名问卷也写**，仅用于限填一次与「我的记录」 |
| limit_once | tinyint | **提交时**对 `survey.limit_once` 的快照 |
| is_valid | tinyint | 1=有效（计入统计）0=已标记无效 |
| invalid_reason | varchar(255) | 标记无效的原因 |
| create_time / update_time / deleted | | 提交时间 / 逻辑删除 |
| **uniq_user** | bigint unsigned | **STORED GENERATED**，见下 |

索引：`uk_survey_user(survey_id, uniq_user)`、`idx_survey_time(survey_id,deleted,create_time)`、`idx_user_time(user_id,create_time)`。

**生成列 `uniq_user`** 是整张表最关键的设计：

```sql
uniq_user BIGINT UNSIGNED GENERATED ALWAYS AS (
  CASE WHEN limit_once = 1 AND deleted = 0 THEN user_id ELSE NULL END
) STORED
```

唯一索引只挂 `(survey_id, uniq_user)`。效果：

- `limit_once=1` 的问卷 → `uniq_user = user_id` → 同一用户第二次提交必然撞唯一键，**并发防线在数据库，不在应用代码**；
- `limit_once=0` 的问卷 → `uniq_user = NULL` → MySQL 唯一索引允许多个 NULL → 可以无限次提交；
- 逻辑删除后 `deleted=1` → `uniq_user` 变 NULL → 释放槽位。

如果没有这个生成列，直接给 `(survey_id, user_id)` 建唯一索引，「可重复填写」的问卷就彻底不可用了。而如果只靠应用层「先查有没有再插入」，两个并发请求会同时通过检查——压测里 10% 的草稿请求就撞出过这个 500。

### 4.2 answer_item — 作答明细

`id` / `sheet_id` / `survey_id`（冗余）/ `question_id` / `option_values`（**JSON**）/ `text_value`（TEXT）/ `number_value`（INT）/ `create_time`。

唯一键 `uk_sheet_question(sheet_id,question_id)`（一份答卷里一题只能有一行）；索引 `idx_survey_question(survey_id,question_id)`、`idx_sheet(sheet_id)`。

**为什么选项答案存 JSON 数组而不是单独一张 `answer_option` 表**：单选存 1 个、多选存 N 个，拆表就要为一道多选题插 N 行，统计时还得两次 `GROUP BY`。JSON 让「一题恒为一行」，统计用 `JSON_CONTAINS` / `JSON_LENGTH`（MySQL 8 原生支持）。实体上配 `@TableName(autoResultMap=true)` + `JacksonTypeHandler` 就能直接把 JSON 列反序列化成 `List<Long>`。

### 4.3 survey_draft — 填写草稿

`id` / `survey_id` / `user_id` / `answers_json`（JSON，NOT NULL）/ `create_time` / `update_time`。
唯一键 `uk_survey_user(survey_id,user_id)`；索引 `idx_user_time(user_id,update_time)`。

草稿不参与统计、不参与导出，唯一用途是「原样还回前端」。所以整卷存一个 JSON，不拆明细行——存 JSON 天然支持「只答了一半」，也不会因为题目被删而写失败。提交成功后删除草稿。

写入用 `INSERT ... ON DUPLICATE KEY UPDATE`（`SurveyDraftMapper.upsert`），不做「先 select 再 insert/update」：后者在 REPEATABLE READ 下修不干净——两个并发请求都判断「不存在」，第二个插入撞唯一键；即使 catch 后重新 select，本事务快照建立于对方提交之前，仍看不到对方那行，二次插入继续冲突。

### 4.4 answer_count 的语义是「有效答卷数」

四条路径必须成对修改：

| 动作 | answer_count |
|---|---|
| 提交答卷 | +1 |
| 标记无效 | −1 |
| 恢复有效 | +1 |
| 删除有效答卷 | −1 |

SQL 里写成 `answer_count = GREATEST(answer_count + ?, 0)`，防止并发或时序错误出现负数。

## 5. 模板（2 张）

### 5.1 survey_template — 模板（问卷结构快照）

`id` / `title`(120) / `description`(500) / `category` / `source_survey_id` / `question_count` / `anonymous_default` / `limit_once_default` / **`structure_json`（JSON NOT NULL）** / `status`（PENDING / APPROVED / REJECTED / OFFLINE）/ `audit_remark` / `audit_by` / `audit_time` / `submit_time` / `rating_count` / `rating_sum` / **`rating_avg`（DECIMAL(3,2) STORED 生成列）** / `use_count` / 审计字段 / `deleted`。

索引：`idx_status_category(status,category,deleted)`、`idx_owner(create_by,status,deleted)`、`idx_rating(status,rating_avg,rating_count)`、`idx_source(source_survey_id)`。

三个设计点：

**① 结构存 JSON，不建 `template_question` / `template_option` 两张表。** 模板只整块读、整块写，从不按题查询或按题聚合。反面例子是 `answer_item`：统计必须按题聚合，所以必须拆。判断标准不是「结构上像不像」，而是「有没有按子元素查询的需求」。

**② JSON 里的选项存文本，不存选项 ID。**

```json
{"questions":[{"questionType":"SINGLE","title":"年级","options":["大一","大二","大三"]}]}
```

模板与来源问卷必须彻底解耦（R-TPL-1）。若存选项 ID，来源问卷一改选项，模板就指向不存在的 ID。存文本则快照自洽。

**③ 存 `rating_sum` + `rating_count`，不直接存平均值。**

```sql
rating_avg DECIMAL(3,2) GENERATED ALWAYS AS (
  CASE WHEN rating_count = 0 THEN NULL ELSE ROUND(rating_sum / rating_count, 2) END
) STORED
```

用户改分时只需 `rating_sum = rating_sum + (新分 - 旧分)`，不用反算平均值（反算会累积舍入漂移）。生成列直接给了一个可排序、可索引的字段，于是「按评分排序」是一个纯粹的索引扫描。

**`rating_avg` 是生成列，所以实体字段必须标 `@TableField(insertStrategy = NEVER, updateStrategy = NEVER)`**，否则写入时报 `The value specified for generated column 'rating_avg' in table 'survey_template' is not allowed`。

### 5.2 template_rating — 评分

`id` / `template_id` / `user_id` / `score`（TINYINT 1~5）/ `create_time` / `update_time`。
唯一键 `uk_template_user(template_id,user_id)` —— 一人一票，改分走 `UPDATE` 而不是再插一行。索引 `idx_user`。

## 6. 配置（1 张）

### 6.1 sys_config — 键值对

`id` / `config_key`(64，`uk_key` 唯一) / `config_value`（TEXT）/ `config_type`（STRING / TEXT / NUMBER / BOOLEAN / PASSWORD）/ `group_name`（SITE / SECURITY / OTHER，`idx_group`）/ `description` / `is_public` / `builtin` / 审计字段 / `deleted`。

内置 10 项：SITE 组 4 项（`site.name` `site.logo` `site.announcement` `site.footer`，全部公开）；SECURITY 组 6 项（`security.default-password` **不公开**、`security.password.min-length` / `max-length` / `require-letter` / `require-digit` / `require-special`，全部公开）。

**唯一键 `uk_key` 只挂 `config_key`，不带 `deleted`。** 这是踩过坑之后的决定：

- 如果 `uk_key(config_key, deleted)`，看起来允许「删了能重建同名键」，但**同一个键第二次被删除时会与上一行的 `(key, 1)` 相撞**——逻辑删除的行不会消失，`(key,1)` 已经被占用。
- 所以保持 `uk_key(config_key)`，在应用层处理「新建同名键」：用 `selectByKeyIncludeDeleted` 查出墓碑行，若 `deleted=1` 就**复活那一行**并覆盖全部属性。

注意 `selectByKeyIncludeDeleted` 必须是自定义 `@Select`——普通 `selectOne` 会被 `@TableLogic` 自动拼上 `deleted=0`，永远看不见墓碑行。

## 7. 索引设计说明

索引不是「给每个字段都加一个」，每一条都能对应一个真实查询：

| 表 | 索引 | 服务的查询 |
|---|---|---|
| sys_user | `uk_username` | 登录按账号查 |
| sys_user | `idx_status(status,deleted)` | 用户列表按状态筛选 |
| sys_user | `idx_audit(audit_status,deleted)` | 注册审核队列（默认查 audit_status=0） |
| sys_user | `idx_phone` | 注册/改资料时查手机号是否被占用 |
| survey | `uk_share_code` | 学生凭分享码进填写页 |
| survey | `idx_owner(create_by,status,deleted)` | 「我的问卷」列表（教师/管理员最常走的路径） |
| survey | `idx_status_time(status,end_time)` | 问卷大厅：`status=PUBLISHED AND end_time>=now` |
| survey | `idx_title` | 列表关键词 `LIKE` 前缀匹配 |
| survey_question | `idx_survey_sort(survey_id,sort_no)` | 取整卷题目并保证顺序 |
| survey_question_option | `idx_question_sort` / `idx_survey` | 按题取选项 / 按卷聚合 |
| answer_sheet | `uk_survey_user(survey_id,uniq_user)` | **限填一次的并发防线** |
| answer_sheet | `idx_survey_time(survey_id,deleted,create_time)` | 答卷列表按提交时间倒序分页 |
| answer_sheet | `idx_user_time(user_id,create_time)` | 「我的填写记录」 |
| answer_sheet | `uniq_user` 上的唯一索引 | 派生 `user_id` 查找 |
| answer_item | `uk_sheet_question` | 保证一题一行 |
| answer_item | `idx_survey_question(survey_id,question_id)` | **统计**：按问卷+题取全部作答 |
| survey_draft | `uk_survey_user` | 一人一问卷一份草稿 |
| survey_template | `idx_status_category(status,category,deleted)` | 模板中心按分类浏览 |
| survey_template | `idx_rating(status,rating_avg,rating_count)` | 模板中心默认按评分排序 |
| survey_template | `idx_owner(create_by,status,deleted)` | 「我共享的模板」 |
| template_rating | `uk_template_user` | 一人一票 |
| sys_config | `uk_key` | 按键读配置（含缓存未命中） |
| sys_login_log | `idx_username_time` / `idx_time` | 按账号查登录历史 / 按时间范围筛 |
| sys_operation_log | `idx_module_time` / `idx_user_time` | 按模块筛 / 按操作人筛 |

**没有做的一件事**：`answer_item` 上没给 `option_values` 建多值索引（MySQL 8.0.17+ 支持 `CAST(option_values AS UNSIGNED ARRAY)`）。统计走的是「一次取出该问卷全部明细，在内存聚合」（见 `docs/api/统计与导出接口.md` 第 8 节），比 SQL 侧逐选项 `JSON_CONTAINS` 扫描更快也更不易错。

## 8. 关键设计决策汇总

| # | 决策 | 备选方案 | 为什么不用备选 |
|---|---|---|---|
| 1 | 限填一次用**生成列 + 唯一索引** | `(survey_id,user_id)` 直接建唯一索引 | 会让「可重复填写」的问卷彻底不可用 |
| 1b | 同上 | 应用层「先查再插」 | 并发下两个请求同时通过检查，压测实测撞 500 |
| 2 | 选项答案存 **JSON 数组** | 单独 `answer_option` 表 | 多选题要插 N 行，统计要两次 GROUP BY |
| 3 | 草稿整卷存 **JSON** | 草稿也拆明细行 | 天然支持「只答了一半」，题目被删也不会写失败 |
| 4 | 模板结构存 **JSON 快照**，选项存**文本** | 建 `template_question` 表、存选项 ID | 模板无按题查询；存 ID 会在来源问卷改动后指向不存在的选项 |
| 5 | 评分存 **sum + count**，avg 走生成列 | 直接存 avg | 改分要反算，反复舍入会漂移 |
| 6 | `status` 不含 `DELETED` | 两处都记录删除 | 会出现两处状态互相矛盾的脏数据 |
| 7 | **不用数据库外键** | FK 约束 | 清理测试数据时的删除顺序会变成雷区；改用应用层校验 + 索引 |
| 8 | 日志表**不加 `deleted`** | 与其他表统一 | 「日志只增不改」是需求，给了删除就等于给了抹证据的入口 |
| 9 | `token_version` 做令牌失效 | 黑名单表 / Redis | 多一个组件、多一份状态不一致风险；改一个整数就够 |
| 10 | 配置表一张 + `is_public` | 公开/私有两张表 | 同一个键可能在两个表里出现，读的时候要判断优先级 |
| 11 | `uk_key` 不带 `deleted`，靠**复活墓碑行**重建同名键 | `uk_key(config_key,deleted)` | 同一个键第二次删除时会与上一行 `(key,1)` 相撞 |

## 9. 从零建库

```powershell
$mysql = "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe"
$db    = "g14(1)"

# 1. 建库（脚本内已含 CREATE DATABASE，此处仅示意）
& $mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS ``G14(1)`` DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci"

# 2. 按序执行五个建表脚本（每个都可重复执行）
foreach ($f in 01_schema_auth, 02_schema_survey, 03_schema_answer, 04_schema_template, 05_schema_config) {
    & $mysql -u root -p --default-character-set=utf8mb4 $db -e "source D:/G14(1)/deploy/sql/$f.sql"
}

# 3. 校验
& $mysql -u root -p --default-character-set=utf8mb4 $db -e "SHOW TABLES"
```

> **注意两点**：① `-e "source ..."` 后面必须再跟库名参数，否则报 `ERROR 1046 No database selected`；② mysql CLI 会因「命令行传密码不安全」的警告返回 exit code 1，这不是失败。

## 10. 容量估算

按课程级规模（用户 < 500、问卷 < 200）估算，单份 5 题答卷的存储开销实测约：

| 表 | 每份答卷行数 | 说明 |
|---|---|---|
| answer_sheet | 1 | 约 160 字节 |
| answer_item | 5 | 含 JSON 列，约 300 字节 |
| sys_operation_log | 1 | 实名问卷才写，约 250 字节 |

1000 份答卷约 1.5 MB。长稳测试期间实测 33 万份答卷时：`answer_item` 约 198 MB（133 万行）、`answer_sheet` 约 53 MB、`sys_operation_log` 约 84 MB。库表增长是线性的，没有需要提前分表的迹象。
