# 首屏加载优化

> 起因：经 Cloudflare 隧道用手机打开，首屏要 10 秒以上。
> 结论：瓶颈不是后端（本机 18ms），而是「首屏字节数」和「串行网络波次」——两者都在前端。

## 1. 先测量，别猜

同一份页面，本机直连与经隧道的对比（python 计时 + `curl -w`）：

| 项目 | 隧道 | 本机 nginx |
|---|---|---|
| TCP + TLS 建连 | 650 / 674 / 690 ms | — |
| 首页 HTML（gzip 后仅 326 B） | 2812 / 1684 / 1862 ms | 3 / 2 / 18 ms |
| 主 JS（1,293,691 B） | **8186 / 5848 ms** | 14 / 12 ms |
| `/api/health` | 1432 / 2582 / 1327 ms | 17 / 15 / 18 ms |

两个结论：

1. **后端不慢**。同一个接口本机 18ms，隧道 1.3~2.6s，差值全是链路。
2. **gzip 一直是开着的**。`Content-Encoding: gzip`、`Cache-Control: max-age=31536000, immutable`，主 JS 实际传输 418,731 B。所以「压缩没开」不是原因，**要用未压缩体积去算**。

再拆一层，看请求是怎么串起来的（playwright 采 `performance.getEntriesByType('resource')`，按开始时间分簇）：

```
第 1 波：1 个请求，0→2762ms       (document)
第 2 波：2 个请求，2763→4631ms    index-*.js + index-*.css
第 3 波：24 个请求，4655→6657ms   LoginView 及其按需组件
```

三个波次，每波约 2 秒。第三波那 24 个请求是**并行**的、最大的才 10KB —— 2 秒几乎全是往返延迟，不是带宽。

于是定位到：**限制首屏的是「波次数量」和「首屏单文件字节数」，而不是压缩、不是后端、不是数据库。**

补充两个环境事实（决定了什么叫"够快"）：

- Cloudflare 免费隧道把流量从 **LAX（洛杉矶）** 出口，`CF-Ray: ...-LAX`。国内用户单次往返约 2 秒。
- 实测隧道吞吐 **47~113 KB/s**，抖动很大。

## 2. 改了什么

### 2.1 Element Plus 改为按需引入（最大一笔）

原来 `src/main.ts` 是全量注册：

```ts
app.use(ElementPlus, { locale: zhCn })
for (const [key, component] of Object.entries(ElementPlusIconsVue)) app.component(key, component)
import 'element-plus/dist/index.css'
```

产物主 chunk 1,293,691 B（gzip 418,731 B）+ 样式 364,997 B，首屏必须走完这一坨。

改为 `unplugin-vue-components` + `unplugin-auto-import` 自动按需（`vite.config.ts`），源码里 `<el-button>`、`ElMessage` 的写法一行不用改。项目实际用到 49 个组件，省掉的是「一次都没用过」的组件和全部 300 多个图标。

**改完必须处理三件事**，否则功能会静默出错：

- **编程式 API 的样式**。`ElementPlusResolver` 只认「模板里写死的标签名」，对 `<script>` 里手动 `import { ElMessage, ElMessageBox } from 'element-plus'` 完全不生效——JS 正常、CSS 缺失。缺的是 `el-message-box` 自己的 `position: fixed` 居中与 `el-overlay` 的全屏遮罩，于是确认框退化成普通块级元素排到 `<body>` 末尾：用户看到的是「退出登录 / 发布问卷的提示框跑到页面最下面」。`main.ts` 显式引入三个入口：

  ```ts
  import 'element-plus/es/components/message/style/css'
  import 'element-plus/es/components/message-box/style/css'
  import 'element-plus/es/components/loading/style/css'
  ```

  主 CSS 从 54,112 B 涨到 65,872 B（gzip 8.2 → 9.94 kB），换回 32 处 `ElMessageBox` 与 170 处 `ElMessage` 的正常布局，很划算。已加单测 `src/__tests__/element-plus-styles.spec.ts` 锁住这三行，防止以后有人「清理未使用 import」时删掉。

- **中文语言包**。原来靠 `app.use(ElementPlus, { locale: zhCn })` 全局注入，按需后没了，分页会显示「10/page」、日期选择器变英文月份。改用 `<el-config-provider :locale="zhCn">` 包住 `<router-view />`（`src/App.vue`）。
- **字符串形式的图标**。菜单是数据驱动的（`{ icon: 'Memo' }` + `<component :is="item.icon" />`），插件只认模板里写死的标签名，认不出字符串。所以 `main.ts` 手工登记 16 个图标（13 个菜单图标 + `ArrowDown` / `Expand` / `Fold`）。**新增菜单项如果图标显示为空，就是漏登记了这里。**

### 2.2 路由守卫不再 await 公开配置

`src/router/index.ts` 原来第一句是 `await useConfigStore().load()`。

这一句把「进入任何页面」串行地绑在一次网络请求之后。本机 18ms 完全看不出来，隧道上这次请求 TTFB 实测 **3096ms**，而且它挡在路由 chunk 之前 —— 等于给首屏白加 3 秒。

站点名有兜底值（`'校园问卷系统'`），配置在 Pinia 里是响应式的，到货后标题/侧边栏/公告会自己更新。所以改成「发起但不等待」，到货后补调一次标题：

```ts
void config.load().then(applyTitle)
```

`afterEach` 里的标题逻辑抽成 `applyTitle()`，导航先完成还是配置先到货都不影响最终正确性。

### 2.3 登录页改为静态引入

28 个路由全是 `component: () => import(...)` 懒加载。但登录页是所有人必经的第一页，它 + 它的按需组件构成第三波那 24 个请求。

改成 `component: LoginView`（静态 import）后，entry 从 271KB 涨到 354KB，但**少一个约 2 秒的波次**。在 60KB/s 的链路上，用 83KB 换一个 RTT 是稳赚。

只对登录页这么做。其他页面（尤其统计页带 ECharts）继续懒加载——把它们塞进 entry 才是真灾难。

### 2.4 试过但撤回：manualChunks 拆 vendor

一开始想「拆成几个 vendor 让浏览器并行下载」，按包名分了 `vendor-element` / `vendor-vue` / `vendor-axios` / `vendor-echarts`。

**实测反效果**：`vendor-element` 变成 957KB（gzip 309KB）并被 `modulepreload` 强制进首屏 —— 原因是按包名归组会把 element-plus 下本来可以懒加载的组件（`el-date-picker` 105KB、`el-table-column` 81KB…）全部拽进一个 eager chunk，按需引入的收益被这个分组整个吃掉。

**教训**：`manualChunks` 适合「一定会用到、且散落在多处的库」，不适合「按需引入 + 路由懒加载」的组件库。已撤回。

## 3. 效果

| 指标 | 改前 | 改后 |
|---|---|---|
| entry JS | 1,293,691 B（gzip 418,731 B） | **354,051 B（gzip 130,510 B）** |
| 首屏 CSS | 364,997 B | **8,258 B** |
| 首屏请求数 | 28 | **5** |
| 串行波次 | 3 | **2** |
| 本机 `/login` | 617 ms | 618 ms（本机本就无感，符合预期） |
| 隧道 `/login`（首次，冷缓存） | **10.99 s** | **5.91 s** |

本机数字没变是正常的——瓶颈从来不在本地。真正的差别在慢链路上：首屏传输量按 gzip 算由约 480KB 降到约 141KB（降 70%），且少一个两秒级的往返。

隧道数字抖动很大（同一天内实测 2.80 ~ 16.42 s），所以**不要拿单次测量当结论**。结构性指标（字节数、请求数、波次）才是可复现的。

## 4. 还没做，以及为什么

| 手段 | 结论 |
|---|---|
| Brotli | nginx 的 `brotli` 模块不是官方镜像自带，要重编译；而 Cloudflare 侧只回 gzip（实测 `Accept-Encoding: br` 无 `Content-Encoding`）。收益约再降 15%，成本不成比例 |
| Cloudflare 边缘缓存 `/assets` | `CF-Cache-Status: DYNAMIC`，免费隧道不回源缓存。哈希命名的静态资源本可以长缓存，但隧道域名每次都变，缓存意义有限 |
| 换国内出口 | 隧道出口固定在 LAX，这是 trycloudflare 免费版的限制。**真正的解法是部署到云服务器**（`docs/deploy/部署文档.md` §1），那时 RTT 从 2000ms 降到 20ms，所有优化都不再必要 |
| 首屏骨架屏 | 不减少等待，只减少「以为卡死」的焦虑。当前 `el-skeleton` 已装，页面加载态已有 |
| 图片/字体 | 项目没有图片资源，字体用系统字体，无可优化 |

## 5. 复现测量

```powershell
# 本机基线（稳定，用来验证没有回归）
node -e "..."   # 见 docs/design 下各模块说明里的 playwright 片段

# 隧道实测（抖动大，看趋势不看单点）
curl.exe -s -o NUL -D - -H "Accept-Encoding: gzip" https://<隧道>/ | Select-String "content-encoding"
curl.exe -s -o NUL -w "size=%{size_download} time=%{time_total}s speed=%{speed_download} B/s`n" https://<隧道>/assets/<主JS>
```

## 6. 顺带修掉的一个测试缺陷

`scripts/e2e-survey.mjs` 里断言「学生的填写记录里没有『查看作答』按钮」，写的是**整张表**都没有。

这个断言只在库是空的时候成立：脚本自己提交的是匿名卷，但库里还可能有别的非匿名记录（本地演示时留下的），那些行本来就该显示按钮。

已改为按行断言——`page.locator('.el-table__row', { hasText: TITLE })` 定位到自己那一行，再断言该行没有按钮。检查的仍然是「这份匿名卷不回显」，但不再依赖「库里没有别的数据」这个与测试目标无关的前提。

同一条经验已写进 `frontend/AGENTS.md`：**任何「列表里应该有/不该有 X」的断言，先想清楚分页、排序和数据残留。**
