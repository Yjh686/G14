# 前端架构说明（认证与后台管理部分）

> 对应代码：`frontend/G14/`
> 覆盖范围：登录认证闭环 + 用户/审核/权限三个后台模块
> 状态：已完成并通过 E2E 冒烟（23 条断言）

---

## 1. 技术选型

| 关注点 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3.5（`<script setup>` + TS） | 组合式 API 便于按功能抽 composable，类型友好 |
| 构建 | Vite 6 | 冷启动与 HMR 快，配置少 |
| 路由 | Vue Router 4（history 模式） | 守卫里做登录/改密/权限三重校验 |
| 状态 | Pinia 3 | 只有认证一个 store，避免过度抽象 |
| UI | Element Plus 2 + 全量图标 | 表格/表单/对话框/抽屉齐全，课程项目开发效率优先 |
| 请求 | Axios | 拦截器可统一注入令牌与拆包 |

脚手架最初是 create-vue 的预发布版依赖（`vue: rc`、`vue-router 5`、`pinia 4`、`vite 8`），已全部降到稳定大版本，避免答辩时踩未发布 API 的坑。

## 3. 关键设计

### 3.1 请求层：一次拆包，错误统一

后端返回 `{code,msg,data,timestamp,success}`，且 `code` 与 HTTP 状态码一致。拦截器在 `code===200` 时**直接返回 `data`**，因此业务代码：

```ts
const page = await userApi.page({ page: 1, size: 10 })   // 直接是 PageResult<UserVO>
```

失败时抛 `ApiError(code, msg)`，页面用 `e instanceof ApiError ? e.message : '兜底文案'` 展示后端中文提示。好处是错误文案只在后端维护一份，前端不重复写「账号已锁定」这类业务语言。

**401 的处理位置**：拦截器不直接 import router/store（会循环依赖），而是暴露 `onUnauthorized(handler)`；`main.ts` 拿到 pinia 与 router 后注册回调，负责清登录态 + 带 `redirect` 跳登录。这样任何接口拿到 401 都会自动回到登录页，页面无需各自处理。

### 3.2 权限模型：只认权限码，不认角色

`useAuthStore` 暴露 `hasPerm(code)` 与 `hasAnyPerm(codes)`，页面与菜单都用权限码判断：

```ts
if (auth.hasPerm('user:list')) { /* 显示用户管理菜单 */ }
```

**不写 `roleCode === 'ROLE_ADMIN'`**。原因来自需求层的决策：学生干部发卷是在 `sys_user_permission` 追加 `survey:create`，该用户角色仍是 `ROLE_STUDENT`。若前端按角色判断，追加权限就失效。

前端权限只做隐显，不是安全边界 —— 每个接口在后端都有 `@RequirePerm`，越权请求返回 403。

### 3.3 路由守卫的四道关卡

| 顺序 | 判断 | 处理 |
| --- | --- | --- |
| 1 | `meta.public` | 放行；已登录访问 `/login` 则回首页 |
| 2 | 无 token | 跳 `/login?redirect=<原路径>` |
| 3 | 有 token 但 `!auth.loaded` | `await fetchMe()` 向服务端确认身份；失败则清态跳登录 |
| 4 | `mustChangePassword` | 强制跳 `/change-password`，后端同时拦截 |
| 5 | `meta.perm` 不满足 | `ElMessage.error` + 跳 `/403` |

第 3 关是刷新场景的关键：token 存在 localStorage 不代表仍有效（可能已被管理员禁用、被重置密码导致 `token_version` 变化），必须用 `/auth/me` 验证一次。

### 3.4 强制改密闭环

管理员重置密码后 `must_change_password=1`，用户登录会拿到该标记。前端：

1. 登录成功后若 `mustChangePassword` 为真，直接跳改密页（优先级高于 `redirect`，否则会先跳到没权限的页面再被弹回）；
2. 改密页隐藏「返回」，只留「退出登录」，避免用户卡在无权限的循环里；
3. 改密接口返回**新 token**（后端 `token_version+1` 让旧令牌失效），store 内 `applyAuth` 换掉令牌，当前设备无需重新登录。

### 3.5 权限配置页的「角色权限 / 追加权限」区分

需求是「只加不减」：管理员能给个人追加权限，但不能撤销角色自带权限。后端提供两个接口，前端做差集：

```ts
rolePermSet = new Set(生效权限.filter(p => !追加权限.includes(p)))
```

渲染时角色自带的勾选框 `disabled` 并标「角色」标签，追加的标「追加」标签。勾选/取消只调用 `grant` / `revoke`，每次操作后重新拉取，避免本地状态与后端漂移。

## 4. 页面清单

| 路由 | 页面 | 必需权限 | 说明 |
| --- | --- | --- | --- |
| `/login` | 登录 | 公开 | 含三个演示账号快填 |
| `/register` | 注册 | 公开 | 提交后进入待审核状态 |
| `/change-password` | 修改密码 | 登录 | 强制改密时锁定其它入口 |
| `/` | 工作台 | 登录 | 按权限展示快捷入口 + 权限自查面板 |
| `/profile` | 个人资料 | 登录 | 姓名/院系/手机号/邮箱可改 |
| `/admin/users` | 用户管理 | `user:list` | 筛选、增删改、启禁用、重置密码 |
| `/admin/audit` | 注册审核 | `user:audit` | 通过/驳回（驳回必填原因）、批量通过 |
| `/admin/permissions` | 权限配置 | `user:grant` | 抽屉内按模块勾选追加权限 |
| `/403` | 无权访问 | 登录 | 守卫跳转目标 |
| `/:pathMatch(.*)*` | 404 | 公开 | 未匹配路径 |

## 6. 后续扩展注意

- 新增业务页面：先在 `router/index.ts` 加路由并声明 `meta.perm`，再在 `MainLayout` 的 `menus` 里补菜单项，两处都读权限码。
- 新增接口：先改 `types/api.ts`，再写 `api/*.ts`，最后页面调用；响应拆包已由拦截器完成。
- 若引入图表（统计模块），建议按需注册 ECharts 组件，避免把主 chunk 再推大。
