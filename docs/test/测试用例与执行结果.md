## 1. 测试分层与分工

| 层 | 工具 | 回答什么问题 | 不负责什么 |
|---|---|---|---|
| 单元测试 | Vitest | 纯函数（字典文案、密码规则、图表 option 构造）是否按预期算 | 不碰网络与 DOM |
| 接口冒烟 | PowerShell + `Invoke-WebRequest` | 每个接口的正常路径、错误码、错误文案、权限边界、数据范围 | 不验页面渲染 |
| E2E | playwright-core + 本机 Chrome | 真实浏览器里点击、跳转、菜单隐显、表单校验、下载 | 不验并发 |
| 压测 | asyncio + aiohttp | 100 并发下延迟与故障率、数据一致性、死锁 | 不验功能正确性 |
| 长稳 | asyncio + jstat | 一整天会不会内存泄漏、连接泄漏、日志撑爆磁盘 | 不验峰值能力 |

**为什么接口冒烟和 E2E 都要写**：冒烟能在 20 秒内跑完 766 条断言，改后端时反馈最快；但它验证不了「菜单里到底有没有这一项」「点保存后跳没跳转」「提示文案在页面上显示出来没有」。E2E 慢（每个脚本 30~90 秒）但能抓住「接口全绿、页面全崩」这类问题——实际开发中确实抓到过：`LogController` 没包 `Result<T>`，接口本身返回正常 JSON，但前端拦截器的 `!('code' in body)` 判断会把它原样透传，日志页必然崩。

## 4. 测试过程中发现并修复的缺陷

按「发现方式」归类。这些不是「测试通过」的注脚，而是这轮测试真正的产出。共 **17 个**真缺陷。

| # | 缺陷 | 发现方式 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 并发首存草稿返回 500 | 压测 `--smoke` 冒烟 | 「先 select 再 insert」在并发下同时判断为不存在 | 改 `INSERT ... ON DUPLICATE KEY UPDATE` |
| 2 | 100 并发整体雪崩（故障率 20%） | 首次 100 并发压测 | Hikari pool=20 被长事务占满，连只读都拿不到连接 | 拆事务 → 再合并为单事务 + 关闭 SQL 日志 |
| 3 | 提交延迟 3458ms | 同上 | 一次提交付 3 次 commit（答卷/计数/日志） | 合并为 1 次 commit |
| 4 | 吞吐卡在 58 req/s | 压测对照实验 | `StdOutImpl` + DEBUG 每请求往 `System.out` 同步写十几行 SQL，9KB/请求 | `NoLoggingImpl` + INFO 级别 → 211 req/s |
| 5 | 草稿保存偶发死锁 | 100 并发第 6 项判定 | `DELETE ... WHERE survey_id=? AND user_id=?` 与 upsert 在 `uk_survey_user` 上争**间隙锁**（冲突双方不是同一行） | 删草稿移出提交事务，改按主键 `deleteById` 只锁一行 |
| 6 | 零答卷导出只剩「汇总」Sheet | 边界验证（openpyxl 回读） | EasyExcel 无数据时不创建 Sheet | 补「暂无答卷」占位行 |
| 7 | `LogController` 响应未包 `Result<T>` | 手工对比 `/api/logs/login` 与 `/api/users` 的响应形状 | 项目无全局 `ResponseBodyAdvice`，前端拦截器会原样透传 | 三个查询方法改返回 `Result<...>` |
| 8 | 导入用户报 NPE | Excel 导入首跑 | MyBatis 只 select 一列且该列该行为 NULL 时，整行映射成 null 元素 | 补 null 判断 |
| 9 | 审核抽屉显示 `SINGLE/MULTIPLE` 原始枚举 | 截图人工复核 | 模板单独写了一份只读列表，忘了走字典 | 改 `questionTypeLabel()` |
| 10 | 评分可点 4.5 星然后 400 | 截图人工复核 | `el-rate` 开了 `allow-half`，后端是 TINYINT | 交互态去掉 `allow-half` |
| 11 | `resubmit` 返回旧驳回原因 | 接口手测 | `update` 只改库不改内存对象 | update 后重新 `load` 再查一次 |
